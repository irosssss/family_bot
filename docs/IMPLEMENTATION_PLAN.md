## 2. Независимая оценка готовности

| Категория | Что известно | Последствие для плана |
|---|---|---|
| Подтверждённый факт | Пользователь согласовал продукт, модели, ART-спецификацию и PIPE. Все нынешние игровые изображения — демо. | Не переоткрывать принятые продуктовые решения без найденного противоречия. Не считать демо production-каталогом. |
| Подтверждённый факт об исходниках | В репозитории есть существующее приложение, отдельная демо, тесты и незавершённые изменения. `npm run lint` запускает `tsc --noEmit`; scripts dev/migrate существуют. | G01 фиксирует исходное состояние и уточняет безопасный запуск. Старые результаты тестов остаются историческими. |
| Обоснованный вывод | Самые дорогие ошибки возникают на стыке доступа, повторных начислений, обязательств по наградам, переноса и визуальной совместимости. | Эти швы получают ранние проверки; количество экранов не служит показателем готовности. |
| Непроверенное предположение | Какие текущие сервисы, UI-компоненты и SQL-фрагменты дешевле адаптировать, чем заменить. | Только аудит по контрактам даёт решение reuse/adapt/replace/defer; каталог рекомендаций не доказывает пригодность. |
| Открытые данные | Условия запуска, остаток security/retention, QDB01, баланс, языки/устройства/бюджеты, реальный импорт, команда и art-ассортимент. | Блокируются только зависимые работы. Тестовые значения помечаются fixture и не становятся пользовательскими правилами. |

Стек сохраняется как исходная техническая база. План не вводит новый движок, микросервисы, универсальный скриптовый язык контента или редактор уровня 2.0 в MVP. Любое такое изменение требует выявленной потребности и оценки сопровождения.

## 5. Как проходит одно согласование

Перед началом блока исполнитель готовит карточку: G-ID, цель и наблюдаемое поведение, конкретные задачи из backlog, затрагиваемые файлы/схемы/среда, зависимости и решения, проверки, ограничения отката, внешние получатели/расходы при наличии. Пользователь подтверждает этот объём. Это правило установленного пользователем поэтапного процесса, а не дополнительная процедура из внешнего skill.

Внутри разрешённого блока исполнитель проверяет предположения, делает работу и исправляет обнаруженные дефекты самостоятельно. Не спрашивает заново разрешение на обычное чтение, локальное редактирование и проверки, уже входящие в карточку. Существенное изменение продукта, среды, передачи данных или объёма сначала оформляется конкретной поправкой. Результат всегда доводится до проверяемого состояния перед вопросом о приёмке.

| Итог карточки | Доказательство | Дальнейшее действие |
|---|---|---|
| Готово к приёмке | Фактический diff/артефакт, команды и результаты, визуальные материалы для UI, известные ограничения. | Пользователь принимает результат; следующая карточка может быть показана в том же сообщении. |
| Нужны исправления | Конкретное расхождение с принятым контрактом, место и проверочный сценарий. | Исполнитель устраняет его внутри разрешённого объёма; вопрос на каждое исправление не требуется. |
| Заблокирована зависимая часть | Открытый ID/внешнее ограничение, что уже выполнено и какой ответ необходим. | Продолжить независимые разрешённые задачи; статус блока не превращается в done. |
| Требуется изменение объёма | Причина, варианты, влияние на поддержку/срок/совместимость и рекомендация. | Принять поправку до зависимого исполнения; не переименовывать невыполненное требование в «позже». |

Публикацию согласуют после готового manifest/digest и проверки кандидата; перенос — после конкретной карты и репетиции. Согласие на локальную подготовку не заменяет эти разрешения. Данные подтверждения содержат минимум необходимого; никаких секретов и семейных персональных данных в Git.

## 6. Сводная карта доказательств

| Область | Основание | Основные этапы | Что предъявлять |
|---|---|---|---|
| Продукт | AC01–AC20 из PRODUCT_CONTRACT по релизной применимости | G03, G07–G11, G14 | Таблица requirement → задача → сценарий → фактический результат; AC20 проверяет доступность основного цикла без боёв уже в MVP, а боевые механики 1.1 в этот проход не входят. |
| Данные и транзакции | DBT01–DBT20 из TRANSACTIONS | G02/G03/G07–G11/G13 | Исполнение на настоящем PostgreSQL в изолированной среде, гонки с разными request IDs, откат после сбоя, сравнение journal/projection. |
| Конвейер | VAL01–VAL15, CPT01–CPT20 | G04, G08, G12–G14 | Отказы повреждённых пакетов, повтор build, конкурентная активация, сохранение приобретённого после rollback. |
| Art и UX | VQA01–VQA20 | G05/G06/G08–G12/G14 | Реальный viewport/WebView, точный кандидат и scene fixture, доступность, локализация, визуальное подтверждение пользователя. |
| Доступ | A01–A16, семейная изоляция, O09 | G03/G11/G14 | Identity не берётся из actorId клиента; чужие read/write запрещены, отзыв действует, PIN и recovery не обходятся простым переключением. |
| Эксплуатация | L01–L08, PIPE06/07, PDB06 | G11/G13–G15 | Restore rehearsal, suppression удалённого, наблюдение, остановка новых выдач, сохранение обязательств. |

У каждого сценария: ID, commit/candidate и версия контракта, среда/fixture, ожидаемый результат, фактический результат, evidence и статус passed/failed/not_run/blocked/not_applicable_with_reason. Наличие списка тестов не означает их прохождение. Не распространять успешный проход fixtures на все возможные устройства и семейные данные.

После изменений кода — `npm run lint`, релевантные unit/API/DB-проверки; перед кандидатом — общая регрессия и build. UI проверяется в браузере и целевых WebView, а документация — ссылками, схемами и согласованностью. Полную регрессию не повторять без новых изменений/неопределённостей. Запуск приложения, которое применяет миграции/seed, допускается только после доказанной изоляции среды.

## 7. Оценка объёма и стоимости сопровождения

| Область | Единица оценки | Что выяснить / измерить |
|---|---|---|
| Backend | Доменная команда с её переходами и конфликтами | Повтор, запрет доступа, побочные эффекты, корректировка, миграция; endpoint count сам по себе недостаточен. |
| Доступ | Способ входа × привязка/отзыв/восстановление × устройство | Общее устройство и собственный Telegram — полноценные сценарии одного профиля, а не две кнопки входа. |
| UI | Пользовательский сценарий × состояния × размеры/режимы доступа | Loading/empty/error/pending, длинные имена, клавиатура, восстановление после сети. |
| Art | Поддержанная комбинация body/pose/view/slot/palette | Время создания, исправления после QA, количество уникальных слоёв/превью и переиспользование. |
| Контент | Новый объект существующего типа и обновление уже приобретённого | Время авторства, валидации, review, build и безопасного rollback; отдельная цена нового типа поведения. |
| Перенос | Тип источника × правило mapping × исключения | Полнота происхождения, ручные решения, время сверки, восстановление и возможное окно остановки записи. |
| Эксплуатация | Один выпуск и один восстановительный прогон | Стоимость хранения retained art/backup, диагностики, обновления зависимостей и доступа операторов. |

После G01 оценка содержит по задаче диапазон трудозатрат, основание, уверенность, исполнителя и внешнее ожидание. После G05/G08 диапазоны пересчитываются по фактической скорости. Календарная длительность учитывает зависимости и доступность людей; сумма человеко-дней не является датой запуска. Резерв на исправления выделяется отдельно по наблюдаемым рискам, без произвольного «точного» процента.

Десятилетний горизонт — регулярная проверка пригодности схем, среды, лицензий и инструментов. Периодичность обслуживания назначается при G14 вместе с ответственным, без создания автоматизаций этим документом. Пересмотр семейных блокировок нужен при измеренной очереди; CDN/редактор/новый renderer добавляются при доказанном ограничении, а не заранее.
