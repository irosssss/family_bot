# Family Chores RPG — Asset Bible основных ассетов

Версия 1.0, 2026-09-07. **ART01–ART08 приняты как спецификация; визуальная проверка впереди.** PDB01–PDB08 приняты как проектная основа с сохранёнными открытыми зависимостями. Все существующие изображения — демо; основные ассеты ещё не созданы и не выбраны. Этот пакет задаёт их спецификацию, а не подтверждает художественное качество будущих файлов.

Пакет: этот документ; [декомпозиция и совместимость](ASSET_COMPONENTS.md); [UX-контракт](UX_CONTRACT.md); [план производства и приёмки](ART_PRODUCTION.md). База данных/метаданные: [Content Dictionary](../data/CONTENT_DICTIONARY.md), [Physical Schema](../data/PHYSICAL_SCHEMA.md); продукт: [PRODUCT_CONTRACT](../PRODUCT_CONTRACT.md).

## 1. Принятые решения спецификации

| ID | Решение | Практический смысл |
|---|---|---|
| ART01 | Общий образ — обжитой семейный дом, спокойный статичный pixel art, ясный интерфейс вокруг сцены. | Дом/личный прогресс остаются главным мотивом; оформление приключения не превращает все экраны в арену. Основной дом станет эталоном после отдельной визуальной приёмки. |
| ART02 | Контент делится на самостоятельные визуальные элементы по смене/совместимости/переиспользованию, а не по каждому нарисованному фрагменту. | Одежда/волосы/питомец/лежанка заменяемы; неподвижная ручка шкафа не требует собственной текстуры. |
| ART03 | Предлагаемые базовые профили: герой 64×80, питомец 48×48, иконка 24×24, сцена дома/уголка 320×240 исходных пикселей. | Это новые кандидаты для пилота, не наследование ULPC или обещание уже проверенной читаемости. До массового производства — проверка размеров на реальном мобильном экране. |
| ART04 | Точные позы, якоря, слоты, семейства тел и правила перекрытия описываются данными профиля. Недостающая совместимость не подменяется растяжением картинки. | Одна вещь может требовать несколько исходных слоёв для разных поз/тел; право владения остаётся одно. |
| ART05 | Питомцы используют общую страницу коллекции и один шаблон уголка; у каждого экземпляра своё сохранённое оформление. | Просмотр не меняет спутника; рядом с ребёнком только выбранный питомец. Домик/лежанка остаются в уголке. |
| ART06 | Игровой art отделён от доступного текстового UI; состояния действий и полномочия выражены явно. | Кнопки/подписи не впечены в фон, никакого обязательного pixel-font для длинного текста или зависимости действия от маленького спрайта. |
| ART07 | Производство проходит через один небольшой вертикальный пилот, затем расширение поддерживаемых комбинаций. | Сначала доказываем, что герой, питомец, дом и интерфейс сочетаются; не генерируем сразу сотни неподходящих вещей. Количество финального контента принимается отдельно. |
| ART08 | Основной каталог развивается ревизиями/пакетами; сцены и права сохраняют ссылки, происхождение и доступ к приобретённому. | Новый сезон/город не создаёт копию семьи/кошелька; демо не становится production-контентом без отдельного решения. |

Приёмка ART означает принятие структуры и направления работы. Она не является одобрением несуществующего изображения, финального набора тел/поз/палитр или разрешением генерации/загрузки во внешний сервис. Числовые профили ниже — гипотезы пилота, явно помеченные как такие.

## 2. Художественное направление

| Область | Предлагаемое правило | Что исключает |
|---|---|---|
| Дом | Уют за счёт композиции, материалов, света и соседства семьи; видимое свободное место вокруг силуэтов | Переполненную мебелью сцену, случайную геометрию каждой комнаты, огромные предметы перед лицами. |
| Персонажи | Узнаваемые лица/силуэты, одежда читается на 1×; дети и взрослые различаются пропорциями в исходнике | Уменьшение взрослого CSS-transform как единственный детский вариант; связь пола/роли с обязательным классом или цветом. |
| Питомцы | Дружелюбный узнаваемый вид, общий свет/контур, умеренный размер рядом с владельцем | Смерть, голод как наказание, плач/страдание за пропуск ухода, огромного спутника поверх людей. |
| Предметы | Читаемая форма и функция до мелкого орнамента; иконка соответствует предмету в сцене | Продажу красивой иконки, визуально не соответствующей применённой вещи. |
| Окружение | Одна согласованная перспектива на визуальный профиль; темы меняют материалы/декор, не ломают якоря | Смешение изометрии, вида сверху и фронтальных спрайтов без специального профиля. |
| UI | Спокойные поверхности, выразительная семейная сцена, один главный акцент действия | Игровой HUD с множеством валют на каждом экране, декоративную панель вокруг каждого текста, анимированный шум. |
| Свет | Для стартового пилота предлагается мягкий тёплый интерьер с единым верхним левым направлением света | Систему реального времени/динамические тени, отдельное рисование всех вещей для каждого часа суток. |
| Контур | Начальный кандидат — 1 исходный пиксель, оттенок зависит от материала/силуэта; проверяется в образце | Обязательную чёрную обводку для всей графики без проверки, размытие контура при экспорте. |

Главный отличительный элемент — семья в живом по композиции, но статичном доме. Остальные экраны наследуют материал поверхностей, цветовые роли, масштаб и контролы после его приёмки. Тема Telegram меняет читаемость оболочки, а не автоматически перекрашивает кожу/шерсть/предметы.

## 3. Исходные пиксели, CSS и экраны

| Профиль-кандидат | Canvas исходника | Использование | Проверка пилота |
|---|---|---|---|
| `hero_home_v1` | 64×80 px, RGBA | Герой и его совместимые слои в доме; 1× = 64×80 CSS px | Лицо и комплект узнаваемы, обувь/голова/оружие не обрезаны. |
| `hero_detail_v1` | Тот же набор 64×80 | Примерочная 2× или 3× при наличии места | Целочисленное увеличение, без отдельного перерисованного героя, меняющего купленный образ. |
| `pet_home_v1` | 48×48 px, RGBA | Спутник и косметика; допустимый силуэт задаёт вид | Контакт с полом, хвост/уши и косметика не закрывают владельца. |
| `pet_detail_v1` | Тот же набор 48×48 | Уголок/предпросмотр с разрешённым целым масштабом | Идентичная косметика, другая поза только при полном комплекте совместимых вариантов. |
| `item_icon_v1` | 24×24 px | Предмет, валюта, статус, навигационный art | Предлагаемый rendered размер 24/48; hit target задаёт UI, не canvas. |
| `item_preview_v1` | 64×64 px | Изолированный товар/яйцо/декор в карточке | Превью показывает тот же вариант, без выдуманного объёма/эффекта. |
| `home_scene_v1` | 320×240 px | Общий дом как сцена внутри страницы | Помещается в 343 CSS px при viewport375 и боковых отступах16; сцена центрируется при 1×, лишнее место принадлежит оболочке. |
| `corner_scene_v1` | 320×240 px | Один открытый уголок | Питомец, место отдыха и игрушка читаются; не загружается полный art всех уголков сразу. |
| `ui_surface_v1` | Кандидат 16×16 px + nine-slice | Только декоративная рамка/текстура растягиваемой поверхности | Контент и фон кнопки работают без этой картинки; края не размыты. |
| `environment_v1` | По отдельному профилю локации | Города/карта/арена позднее | Размер не выводится из демо-карты; до создания нужен собственный масштаб/anchors/бюджет. |

Canvas — монтажная область, не обязательная площадь непрозрачного силуэта. Layers одной сборки имеют одинаковую координатную систему. Crop и trim допустимы только с сохранённым offset и проверенным преобразованием обратно в canvas; произвольное удаление прозрачных полей без метаданных запрещено.

Начальный способ масштабирования сцены: выбрать целый коэффициент k≥1, при котором исходник помещается в доступную ширину; центрировать, свободное пространство отдать фону оболочки. Не растягивать всю страницу вместе с текстом и не использовать дробный scale для повышения «заполненности» сцены. На viewport320 убрать внешние поля именно у сцены, сохранив текстовые отступы. На более узком доступном пространстве переключиться на доступный список семьи/детальное представление; UI не должен требовать горизонтальной прокрутки всей страницы.

На desktop сцену можно показать 640×480 при k=2 рядом с задачами. Это не фиксирует ширину всей страницы и не требует гигантских кнопок. Device pixel ratio не умножает размеры CSS-кнопок; фактическую растеризацию/nearest-neighbor нужно проверить на целевых WebView. Визуальный тест важнее наличия свойства image-rendering.

## 4. Модульный контракт сборки

Каждый appearance/pet/scene snapshot разрешает exact ContentRef → VisualBinding → AssetRef + VisualProfile revision. Сборщик не угадывает слой/тип по имени PNG. Полный набор игровых полей уже определён в CONTENT_DICTIONARY; следующие authoring-уточнения предлагаются для визуальных профилей.

| Поле профиля / варианта | Тип | Назначение |
|---|---|---|
| `pose_key`, `view_key`, `body_family_key` | Key | Конкретная поза, направление и семейство пропорций; различаются от ID владельца. |
| `canvas_width_px`, `canvas_height_px`, `pixel_grid` | Positive integer | Общая сетка сборки; значения профиля-кандидата становятся обязательными только после пилота. |
| `layer_key`, `layer_order` | Key, integer | Стабильный зарегистрированный слой и порядок внутри сборки. |
| `anchors` | List<NamedAnchor> | floor_contact, hand_grip, head_top, seat_contact, companion_contact и другие объявленные точки. |
| `occupied_slots`, `hidden_layers` | Set<Key> | Например, комбинезон занимает torso+legs; капюшон скрывает конкретную часть волос. Не произвольный z-index от автора товара. |
| `required_variants` | Set<VariantKey> | Какие комбинации pose/view/body обязательны именно этому типу контента. |
| `attachment_rule`, `occlusion_rule` | Versioned registry refs | Разрешённые способы крепления/перекрытия; произвольный исполняемый код в пакете не допускается. |
| `contact_shadow_binding` | AssetRef nullable | Отдельная тень только если зависит от положения/силуэта; без дублирования запечённой тени. |
| `safe_bounds`, `interaction_anchor` | PixelRect, NamedAnchor nullable | Видимая область и точка для внешнего доступного контроля; не разрешение создать крошечную hit-зону. |
| `fallback_policy` | Closed registered rule | Ошибка ресурса → нейтральное представление/повтор загрузки; не показывать другую купленную вещь под видом выбранной. |

VariantKey — явный tuple(body_family,pose,view,palette_variant), а не свободная строка, из которой надо парсить игровой смысл. Палитровая замена допускается лишь через принятые индексы/маски материалов; CSS hue-rotate всего героя не применяется к коже, глазам и одежде одновременно.

Раскладка семьи также принадлежит данным: `SceneLayout` имеет registry_id/revision, scene_profile_ref и список `member_slots`. Slot содержит slot_key, допустимые role/body/pose, floor/seat/companion anchors, bounds для пары владелец+pet, depth_group и label policy. Ёмкость кадра выводится из списка слотов; кандидат «4 участника» не становится константой в компонентах. Runtime привязывает разрешённые MemberProfile к этим слотам; в системном layout нет имён/ID реальных детей и обязательных персонажей «папа1/мама1». Для большего состава используются группы и доступный список по UX-контракту, без потери членов семьи.

Имена профилей в таблице раздела 3 — рабочие метки кандидатов; в реестре устойчивый ID не содержит номер ревизии: например `core:visual_profile/hero_home`, revision=1. Новая несовместимая система геометрии требует явной версии/совместимого переноса, а не тихого изменения файла профиля под прежним номером.

## 5. Совместимость и цена производства

Базовая единица владения — ContentDefinition/ownership_key. Количество PNG зависит от вариантов. Если вещь поддерживает B семейств тел, P поз и V видов, производственная матрица содержит до B×P×V сборок. Это оценка комбинаций, не обещание генерировать все варианты или хранить каждый цвет отдельным файлом. Один общий слой можно использовать в нескольких ячейках только после проверки геометрии и семантики.

Начальный пилот использует один утверждаемый вид камеры и минимальный набор поз. Кандидаты поз: neutral_stand и home_seated; seated нельзя получить сжатием стоящего спрайта. Если выбран домашний сидячий состав, его body/clothing/hand/контактные варианты обязательны до приёмки дома. Количество взрослых/детских семейств пропорций и поз не фиксируется миллионами комбинаций заранее.

Любая новая поза/семейство тела расширяет матрицу. Автор пакета явно заявляет поддержку; предмет с неполной матрицей не продаётся как универсальный. Несовместимость показывается до покупки. Купленная вещь не снимается молча при смене тела: preview сообщает конфликт и предлагает явный допустимый выбор; правила смены базового образа не дают бесплатных прав.

## 6. Состояния и ошибки ресурсов

| Ситуация | Поведение |
|---|---|
| Файл не загрузился | Текст/действие доступны; компактная заглушка с повтором, внутренняя диагностика exact asset revision. Не сбрасывать выбор владельца. |
| Несовместимый предмет при подготовке пакета | Блок публикации соответствующей комбинации; не выпускать с надеждой на CSS-поправку. |
| Неизвестная схема профиля на клиенте | Пакет не активируется для неподдерживаемого клиента; ограниченное сообщение обновления, не падение всего дома. |
| Декор скрыт перекрытием | Validator/preview отмечает проблему; нельзя считать купленный предмет «применённым и видимым» без проверки. |
| Выбранный pet отсутствует в коллекции | Сервер отвергает нарушение владения; клиент не назначает первый элемент списка автоматически. |
| Снята продажа/завершён сезон | Полученные права и разрешимые ревизии сохраняются по принятой политике; не удалять их файлы с CDN только по дате сезона. |

## 7. Папки и имена — проект разделения

Это функциональная раскладка будущего производства. Подробная схема manifests/build/release будет отдельным этапом контентного конвейера; сейчас папки и файлы с графикой не создаются.

```text
content-source/
  schemas/                     # закрытые контракты авторских данных
  registries/                  # types, palettes, slots, visual profiles
  packages/<package-slug>/
    definitions/<kind>/<slug>.json
    localization/<locale>.json
    credits/
art-source/<asset-slug>/
  source/                      # редактируемые исходники, не runtime
  references/                  # разрешённые референсы
  exports/                     # кандидаты файлов
  review/                      # листы совместимости и доказательства
content-build/                 # воспроизводимая сборка, не источник истины
public/assets/game/<package-slug>/<release>/
  <asset-slug>__<variant>__r<asset-revision>.png
docs/art/                      # правила и протоколы приёмки
```

ContentId остаётся `core:pet/cat`; файловое имя может измениться независимо от него. Slugs/variant tokens — lowercase ASCII snake_case; без имён детей, пробелов, «final_final» и emoji. Namespace и точная revision хранятся в manifest; runtime не выводит ID из пути. Байты immutable-пути не перезаписываются. Отдельные файлы демо остаются на местах до разрешённой замены; эта схема не команда переноса текущих каталогов.

## 8. Что ещё нужно доказать

Палитра, контур, камера, пропорции, конкретные poses, числовые профили и читабельность должны пройти пилот. Размеры пакета/памяти/первой загрузки — измеряемые O13; здесь нет выдуманного «AAA-бюджета». Страны/возрасты, переводы, QDB01 и конкретный импорт остаются отдельными зависимостями. Ни ссылка на стандарт, ни таблица ассетов не заменяют visual QA.
