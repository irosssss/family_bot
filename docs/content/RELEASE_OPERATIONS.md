# Family Chores RPG — выпуск и сопровождение контентных пакетов

Версия 1.0, 2026-09-07. **PIPE05–PIPE08 приняты пользователем как проект конвейера.** Основа: [конвейер](CONTENT_PIPELINE.md), [контракты](AUTHORING_CONTRACTS.md), [транзакционная модель](../data/TRANSACTIONS.md). Ничего не загружено, не опубликовано и не активировано этим документом.

## 1. Состояния и полномочия

| Объект | Состояния | Кто меняет / ограничение |
|---|---|---|
| Авторский материал | draft → ready_for_build | Автор namespace; нет права назначить себе production approval. |
| Candidate | built → validated → reviewed → approved; отдельно failed/superseded | Проверяющие этапы и разрешённый reviewer, exact fingerprint/digest. Нет действующего approval у иного результата. |
| PackageRelease | published, неизменный состав | Publication service по разрешению; failed upload не published. Отзыв/продажи — отдельная управляющая запись, не изменение bytes. |
| ActivationSnapshot | current / historical | Атомарный переход указателя с expected revision. Неактивный пакет может требоваться для старых приобретений. |
| AdmissionPolicy | enabled / disabled для новых выдач | Управление продажами/выдачами; не уничтожает retained references. |
| Artifact | staged → published → retained → eligible_for_cleanup | Storage/GC по проверяемой достижимости и политике, не family admin кнопкой. |

Автор/технический reviewer/art reviewer/оператор выпуска — роли производственного процесса, не новые роли родителей/детей в приложении. Один человек может выполнять несколько ролей в маленькой команде, но действия и основания различаются. Семейное admin-право не даёт публикацию глобального каталога. Этот документ не создаёт аккаунты этих ролей и не назначает их пользователю автоматически.

## 2. CI и ручная проверка

| Участок | Автоматические проверки | Человеческая приёмка |
|---|---|---|
| Изменение авторских JSON | Parse/closed schema/ID/ref/semantics, affected graph | Правильность смысла предмета и заявленной совместимости. |
| Изменение бинарного art | Bytes/digest/MIME/alpha/frame count/geometry/variant coverage | Силуэт, контакт, перекрытия, соответствие превью и основного вида. |
| Изменение текста | Ключи/аргументы/plural syntax/fallback | Понятность ребёнку, контекст, переносы/длинные строки. |
| Изменение схемы/handler | Матрица producer/consumer, миграционные fixtures, регрессии | Допустимость новой механики и стоимости сопровождения. |
| Candidate build | Exact lock, повторяемость, runtime/private projection split | Новый fingerprint заново согласуется в затронутых областях. |
| Release | Полнота uploaded files, approved digest, compatibility/readiness | Конкретное разрешение публикации и затем активации. |

Проверки PR не получают production write credentials. Pull-request preview работает на синтетических fixtures с доступом к нужному art по разрешённой области; реальные профили/кошельки не используются ради удобства демонстрации. Импорт авторских материалов в сторонний генератор/дизайн-сервис — отдельное разрешаемое действие, не скрытая стадия build.

## 3. Предпросмотр

Preview читает тот же скомпилированный runtime manifest candidate, который предлагается выпустить. Нельзя подменить его «похожими» dev imports из src/demo/catalog.ts. В preview видно candidate_id, fingerprint, profile revisions и версия оболочки; пользовательская игровая сцена при этом не содержит этих технических меток как часть будущего UX.

Обязательные fixtures из ART: разные составы семьи, базовый/купленный комплект, пары пересекающихся слоёв, два независимых уголка с общим декором, большой каталог превью, длинные локализованные строки, pending/refused/unknown-result состояния, разные режимы доступа. Визуальные доказательства привязаны к viewport, locale, theme, fixture version и candidate digest. VQA01–VQA20 из ART остаются будущими проверками, пока прототип и assets не созданы.

Preview не активирует предложения, не начисляет стартовые права и не выполняет внешние сообщения/покупки. Закрытие preview ничего не меняет в существующем доме. Оценка на склеенном concept фиксирует художественное направление; она не доказывает поддержку реальных слоёв/выбора экипировки.

## 4. Безопасная последовательность публикации

1. Зафиксировать approved candidate и его manifest digest; проверить namespace/release права, актуальность art/rights/technical approvals и отсутствие иной опубликованной версии под тем же package/version.
2. Подготовить все файлы в отдельной staging-области. Повтор загрузки использует те же immutable bytes; другой digest под занятым immutable key — ошибка, не overwrite.
3. Проверить чтением из целевого storage все объявленные файлы: digest/размер/тип; наличие только локального build недостаточно.
4. Разместить проверенные immutable runtime files и manifest. Ещё не менять active pointer и не открывать новые offers.
5. Одной publication-транзакцией зарегистрировать PackageRelease, нормализованные точные ссылки, manifest digest, operation и evidence одобрения. Если DB commit не состоялся, файлы остаются неактивными staged/orphan объектами для поздней проверяемой очистки.
6. Вернуть результат published. Активация — отдельная операция ниже, с проверкой полного набора зависимостей и поддерживаемых форматов.

Загрузка файлов и DB-транзакция не притворяются одной атомарной транзакцией разных хранилищ. Ошибка на шаге 3 не становится частично доступным магазином. Idempotent повтор различает уже опубликованный тот же digest и конфликт. Publication не запускает миграции из content files.

## 5. Атомарная активация набора

Принятое уточнение физической модели PIPE06: `ActivationSnapshot` фиксирует весь текущий production-набор пакетов, а существующий ReleaseActivation отражает изменение конкретного пакета внутри этого снимка. Последовательная запись нескольких независимых pointers без снимка запрещена.

| Запись | Поля | Проверка |
|---|---|---|
| ActivationSnapshot | snapshot_id EntityId, scope_key, schema_version, package_refs с exact manifest digests, compatibility_ref, snapshot_digest, created_at, operation_id | Неизменный snapshot; один package version на ID в текущем графе. |
| ActivationHead | scope_key PK, snapshot_id FK, state_revision | CAS по expected revision; MVP global scope, сложный семейный rollout не добавлен автоматически. |
| ActivationChange | operation_id, previous_snapshot_id, next_snapshot_id, reason, actor_ref, activated_at | История управляющего действия; не персональные игровые эффекты. |

В транзакции операции активации проверяются published/approved releases, замыкание зависимостей, необходимые schema/handler capabilities, готовность отдельно разрешённых миграций и сохранение доступа к приобретённым старым revision. Затем создаётся snapshot и меняется head. Параллельная активация с устаревшим expected revision получает конфликт и не перезаписывает новый набор.

Семейная команда, зависящая от текущего каталога, после family lock берёт согласованный snapshot/admission state; при необходимости удерживает SHARE lock head до commit, чтобы продажа и выключение новых выдач имели определённый порядок. Активация берёт UPDATE lock head и не пытается взять семейные строки в обратном порядке. Любое изменение этого порядка требует аудита PDB04.

В API клиент передаёт ожидаемые offer/content revisions и activation snapshot. При устаревших условиях новой покупки сервер возвращает обновлённую карточку/конфликт, а не тихо списывает новую цену. Уже созданные reservation/order/settlement продолжают использовать закреплённые условия по DAT/R, даже если текущая витрина изменилась. Клиентский manifest не заменяет серверную проверку прав, цены и источника действия.

## 6. Кеши и частичная доставка

| Что кешируется | Политика проекта |
|---|---|
| Immutable бинарные файлы/manifest по version/digest | Долгий публичный кеш только для действительно публичного не персонального контента; exact HTTP TTL согласуется при hosting. Путь не перезаписывается. |
| Current activation pointer | Перепроверяемый ответ control API с revision/ETag либо no-store; нельзя считать кешированный pointer бессрочным источником допуска новой покупки. |
| Семейные данные/режим доступа | Отдельная private/no-store политика; никаких общих CDN-кешей для wallets, sessions или персональных exports. |
| Превью коллекции | Ключ включает pet/appearance revision и manifest digest; исходное право не выводится из наличия thumbnail. |
| Целый уголок/сцена | Текущий scene package и нужные layers; управление памятью по O13, а не бессрочный кеш всех коллекций. |

Клиент сначала получает целостный descriptor, затем необходимые ресурсы. При ошибке загрузки сохраняет известный выбранный образ/право, показывает предусмотренное ограниченное состояние и повторяет получение нужных файлов; не смешивает новый torso со старым body profile. При first load без пригодного каталога доступны shell/объяснение ошибки, а не попытка исполнить неизвестный handler.

HTTP-кеширование опирается на [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html). Конкретные TTL, CDN invalidation и offline-подписи ещё относятся к реализации/hosting. Публичный digest URL сам по себе не является механизмом авторизации личных файлов.

## 7. Откат, отзыв и сохранение прав

| Сценарий | Действие | Что сохраняется |
|---|---|---|
| Ошибка нового appearance/пакета до новых выдач | Вернуть ранее проверенный snapshot после проверки совместимости текущего runtime | Игровые данные/кошельки не меняются. |
| После выпуска уже есть новые покупки | Остановить новые выдачи ошибочного content/offer; вычислить rollback closure и retained refs | Уже полученные права и их изображения остаются разрешимыми либо идут через явно принятый совместимый replacement plan. |
| Ошибка зависимости нескольких пакетов | Откатить согласованный набор целиком, а не один несовместимый пакет посередине | Все зависимые profile/schema refs существуют; старые сохранения проверяются. |
| Сезон закончился | Выключить новые предложения/активацию по политике | Приобретённый декор, pet и corner не удаляются автоматически. |
| Ресурс нельзя больше распространять | Отдельный incident/rights decision, прекращение доступа к проблемному binary, согласованный replacement | Entitlement не стирается; UI сообщает ограничение, не показывает случайную замену как купленную вещь. Конкретная политика разрешается по фактическому случаю. |
| Изменился код/DB-schema | Использовать отдельный план восстановления приложения/данных | Откат manifest не исполняет обратную SQL-миграцию и не восстанавливает старую семью поверх новой. |

Rollback-план содержит previous/next snapshots, affected packages/definitions, acquired references, поддерживаемые consumer versions, требования отдельной миграции, ожидаемые ограничения и доказательства тестового восстановления. Если прежний snapshot несовместим с уже развёрнутым кодом или новыми правами, «переключить назад» блокируется; выбирается исправление вперёд либо отдельно проверенный перевод состояния.

## 8. Удаление неиспользуемых файлов

GC использует mark-and-sweep только после выбранной retention/grace политики и повторной проверки ссылок. Корни достижимости: текущие snapshots; действующие rollback pins; retained acquisitions/appearance/corners/house; незавершённые orders/reservations; опубликованные пакеты по политике хранения; разрешённые preview/review pins. Обход транзитивный — удаление зависимости не допустимо лишь потому, что на неё нет прямой ссылки от пользователя.

Сначала сформировать GC plan с перечнем кандидатов, digest, причиной недостижимости и evidence. Затем отдельно разрешённое выполнение повторно сверяет поколение графа/активации и ссылки. Если после анализа появился новый pin/покупка, файл исключается из удаления. Runtime source provenance не удаляется раньше обязательного evidence без принятой политики.

Демо-статус не означает «не используется»: перед удалением текущего файла сохраняются требования проекта — поиск runtime-ссылок и проверка используемых ресурсов. Удаление персональных данных и GC публичных PNG — разные процессы. Старый source snapshot не должен восстановить удалённую личность при повторном импорте.

## 9. Приёмочные сценарии конвейера

Каждая строка — будущий тест реализации. В этом документальном этапе они не запускались.

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| CPT01 | Два record с одним ID/revision и разными свойствами | REVISION_REWRITE, не последний победивший файл. |
| CPT02 | Число coins за пределами точного Number / дробь | Decimal string сохраняется; неверное представление отвергнуто, не округлено. |
| CPT03 | Duplicate JSON keys / неизвестное поле | Parse/schema error до канонизации/компиляции. |
| CPT04 | Traversal, symlink наружу, регистровая коллизия | Нет чтения/публикации постороннего файла, точная ошибка. |
| CPT05 | Цикл/отсутствующая required dependency | Resolve не создаёт candidate с частичным manifest. |
| CPT06 | Две active версии одного package_id | Конфликт набора; старый retained release при этом разрешено хранить отдельно. |
| CPT07 | Один бинарный вход изменён после review | Fingerprint/digest изменён, approval недействителен для нового candidate. |
| CPT08 | Два build одинаковых frozen inputs | Совпадают публикуемые bytes/digests; технические времена отчёта могут различаться. |
| CPT09 | Изменён порядок полей JSON/множеств | Semantic hash стабилен; изменение порядка значимых слоёв меняет digest. |
| CPT10 | Несовместимый pet/hat/corner profile | Candidate не проходит required visual compatibility. |
| CPT11 | Отсутствует перевод/не совпадают аргументы | Соответствующий locale/package release блокируется. |
| CPT12 | Private rights path/имя fixture в public projection | PRIVATE_FIELD_EXPOSED; публичный артефакт не создаётся. |
| CPT13 | Прервалась загрузка до всех файлов | Current pointer прежний, published/active не объявлены. |
| CPT14 | Повтор публикации того же version/digest | Один release/операция; иной digest под тем же version отклонён. |
| CPT15 | Две одновременные активации | Один expected revision проходит, второй получает conflict. |
| CPT16 | Новая покупка из устаревшей витрины / старый pending order | Новая требует актуальных условий, старый order сохраняет обещанные. |
| CPT17 | Откат после получения новой вещи | Право/разрешимость retained revision сохранены; wallet не откатан. |
| CPT18 | GC-план устарел из-за нового pin | Связанный файл не удалён; generation повторно проверен. |
| CPT19 | Клиент не поддерживает schema/handler | Нет исполнения неизвестного контракта, ясное ограниченное состояние. |
| CPT20 | Закончился сезон / большой pet catalogue | Полученное доступно; полные сцены загружаются по требованию, измерены бюджеты. |

## 10. Граница готовности

Подготовлены: статусы, роли, входы/выходы, правила lock/hash/projection, публикация/активация/откат/GC и будущая проверочная матрица. Не выполнены: schema registry всех активных типов, CLI/compiler, CI integration, storage credentials/hosting, синтетический прототип, основные ассеты и visual QA. Конкретные библиотеки, resource limits и полномочия оператора выпуска выбираются в плане реализации; отсутствие этих решений не заменяется обещанием готового production-конвейера.
