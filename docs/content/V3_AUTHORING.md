# Как добавлять и менять контент V3

Актуально: 22.09.2026. Входная инструкция для текущего локального приложения.
Принятый полный конвейер: [CONTENT_PIPELINE](CONTENT_PIPELINE.md),
[AUTHORING_CONTRACTS](AUTHORING_CONTRACTS.md), [RELEASE_OPERATIONS](RELEASE_OPERATIONS.md).
Новые правила не заменяют эти контракты: ниже адаптер существующей V3 до production-сборки.

## Где что находится

| Папка | Назначение |
|---|---|
| `.agents/skills/` | инструкции агентам, закреплённый источник и лицензия |
| `content-source/v3/` | редактируемые определения локального каталога |
| `src/v3/content/` | адаптер каталога для UI и смысловая проверка |
| `src/v3/` | интерфейс V3 и локальная бизнес-логика |
| `src/target/content/` | существующий production-конвейер G04; не заменять локальным адаптером |
| `scripts/content/` | CLI проверки действующего каталога V3 |
| `tests/v3-content.test.ts` | защита ID, связей, файлов, совместимости гардероба |
| `public/assets/game/wardrobe-pilot/v3/` | действующие 28 оригинальных PNG; историческое имя URL сохранено |
| `public/assets/game/v3-ui/` | действующие изображения сцен и интерфейса |
| `docs/content/` | контракты и эта инструкция |
| `docs/art/` | художественные правила и подготовка материалов |
| `docs/reviews/` | аудиты и результаты приёмки |
| `docs/archive/` | уже архивированные документы |
| `work/`, `output/` | рабочие материалы, старые эксперименты, доказательства проверок; не каталог магазина |

Legacy `src/components`, `src/services`, `src/db` и старые ассеты не являются новым
каталогом V3. Не переносить/удалять их без проверки потребителей. Наличие файла в
public не даёт предмет автоматически. Каталог V3 сейчас содержит только его контент;
старые питомцы/ULPC и production-fixtures не были переименованы или импортированы.

## Три разных идентификатора

- Определение предмета: `core:outfit/father_basic_1`. Стабильно, никогда не переиспользовать.
- Ресурс картинки: `core:asset/father_basic_1`. Ссылается на PNG; замена пути не меняет предмет.
- Экземпляр у пользователя/запрос/операция: отдельный ID состояния. Это не ID определения.

Стиль `core:outfit_style/basic_1` объединяет четыре комплекта разных персонажей.
`legacyId: basic-1` — старый ключ покупки в журнале локальной V3; оставлен специально.
Не заменять его каноническим ID без миграции журнала и тестов. В production используются
ContentRef с точной ревизией и серверные instance IDs по DATA_CONTRACT.

Формат: `namespace:kind/slug`, lowercase ASCII snake_case, без пробелов и имён людей.
ID хранится в JSON явно и не вычисляется из русского названия или пути. `revision` —
положительное целое; переименование отображаемого названия не означает новый предмет.

## Добавить комплект

1. Проверить Figma и существующие assets: сначала использовать готовое.
2. Для нового стиля добавить строку в outfit-styles.json с уникальными `id`, `legacyId`,
   названием и согласованной ценой. Новая цена не является разрешением менять старые цены.
3. Подготовить четыре варианта (папа/мама/дочь/сын). Зарегистрировать картинки в assets.json.
4. Добавить четыре записи outfits.json: собственный ID, avatar, styleId, assetId, revision.
5. Зафиксировать происхождение в ASSET_MANIFEST. `local_preview` не означает проверку прав
   для публичного выпуска. Подробные исходники и материалы проверки не помещать в public.
6. Выполнить проверки ниже. Проверить все четыре примерки и отображение надетого комплекта
   в «Сегодня». Новый тип предмета (волосы/мебель/питомцы) сначала требует обработчика
   и схемы; запись произвольного kind сама по себе не создаёт функционал.

## Заменить изображение

Для текущей локальной V3: сохранить ID предмета и ресурса, добавить новый файл с явной
ревизией, обновить path/revision и манифест. Проверить прозрачность и размеры. Старый файл
сначала проверить поиском по src/docs/fixtures; не удалять автоматически.
Для опубликованного production-контента использовать неизменяемые ревизии G04.

## Локации и боссы

locations.json хранит названия и точки карты (проценты относительно изображения).
`playable`, `preview`, `planned` отражают готовность контента, не прогресс конкретной семьи.
Парк открывается по состоянию кампании, не ручной сменой статуса в JSON.
Добавление строки босса ещё не подключает новую главу: текущая механика реализует только
первого босса. Следующая глава требует расширения переходов кампании и тестов сохранения.
HP60 и сила10 закреплены в domain v1: не менять их через каталог без версии правил/миграции,
поскольку старые события журнала воспроизводятся. Каталог босса проверяется на совпадение.

## Проверки

```sh
npm run content:v3:validate
npm run lint
npm test -- tests/v3-content.test.ts tests/v3-domain.test.ts tests/v3-session.test.ts tests/v3-campaign.test.ts
```

Валидатор проверяет структуру, уникальность ID/старых ключей, ссылки, полноту вариантов,
бесплатную базу и наличие файлов внутри public. Это не проверка художественного качества,
прав использования и готовности публичного запуска. После изменения изображения —
браузер375/390, скриншот, проверка старого сохранения без сброса семьи.

## Безопасное расширение

Не удалять определения купленных предметов, не переиспользовать ID и не редактировать
исторические цены/награды для replay журнала без миграции. Снятие с продажи и изъятие
из гардероба — разные действия. Числовой баланс, экономика и новые функции согласуются
по правилам проекта. Исторические планы сохраняются; новый документ должен ссылаться
на существующий контракт, а не создавать параллельную «версию истины».
