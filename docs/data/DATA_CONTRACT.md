## 2. Примитивы и составные типы

В словарях `!` означает обязательное ненулевое поле; `?` — поле присутствует, но допускает `null` при описанном условии. Отсутствие свойства в полном каноническом объекте не равно `null`. Команды изменения имеют собственную схему: отсутствующее поле означает «не изменять» только там, где это явно разрешено. Ни один nullable FK не получает молчаливый fallback.

| Тип | Представление | Ограничение |
|---|---|---|
| `EntityId` | UUIDv7, строка в JSON | Создаётся сервером; формат, версия UUID и уникальность проверяются. Время внутри UUID не заменяет `created_at` и не определяет порядок конкурентных операций. |
| `ContentId` | `namespace:kind/slug`, например `core:pet/cat` | Строчные ASCII: `^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*/[a-z][a-z0-9_]*$`. После публикации неизменен. Перенос файла, перевод и смена категории его не меняют. Это символический ID, не путь. |
| `Key` | ASCII `snake_case` | Ключ поддерживаемого вида, слота или контракта. Существование проверяется по соответствующему реестру; неизвестное значение не исполняется. |
| `TextKey` | Строка вроде `pet.cat.name` | Стабильный ключ системной локализации. Не хранит готовый текст и не является пользовательским именем. |
| `Text` | Unicode-строка | Пользовательский текст, без исполнения HTML/скрипта. Ограничения длины по полю обязательны до API-реализации; не задаются произвольным единым лимитом для всего продукта. |
| `UInt` | Строка `0` либо строка из цифр, начинающаяся с 1–9 | Неотрицательное целое; точный диапазон хранения выбирается на физическом этапе, переполнение всегда отклоняется. Это всегда JSON string, не JSON number. |
| `Int` | Каноническая десятичная строка со знаком при отрицательном значении | Для дельт; нет `-0`, дробей, экспоненты и ведущих нулей. Баланс сам по себе не отрицателен. |
| `SmallInt` | JSON integer | В пределах безопасного целого JSON-клиента и ограничения конкретного поля; размеры/индексы/дни, не монеты. |
| `Revision` | Положительный JSON integer | Начинается с 1, монотонен в своей области; ограничения диапазона обязательны. Ревизия состояния не перезаписывает номер опубликованного контента. |
| `SchemaVersion` | Положительный integer | Версия конкретного контракта сериализации; не номер миграции БД. |
| `PackageVersion` | Строка SemVer | Версия выпуска пакета, например `1.0.0`; правила диапазонов/предрелизов будут закреплены в конвейере. |
| `Instant` | RFC 3339 UTC, например `2026-09-07T12:00:00.000Z` | Серверный момент события. Для интервалов используется `[start_at,end_at)`; `start_at < end_at`. |
| `LocalDate` | `YYYY-MM-DD` | Проверка действительной даты, а не только регулярного выражения. Семейная зона задаёт смысл даты. |
| `ZoneId` | Идентификатор IANA, например `Europe/Moscow` | Проверяется по используемой базе зон. Смещение UTC не заменяет историю зоны. |
| `Digest` | `{algorithm: Key, value: Text}` | Для ресурсов предлагается `sha256`: 64 строчных шестнадцатеричных символа. Алгоритмы из закрытого реестра. Хеш файла не является доказательством лицензии; хеш запроса требует отдельно заданной канонизации. |
| `Ref<T>` | ID записи типа T | Проверяются тип, существование, допустимое состояние, семейная область и полномочия. Формат берётся из ID целевого типа. |
| `ContentRef` | `{definition_id: ContentId, content_revision: Revision}` | Точная опубликованная ревизия. «Последняя версия» допустима как политика каталога, но не как ссылка сохранённой покупки. |
| `TypedPayload` | `{contract_id: Key, schema_version: SchemaVersion, value: object}` | `value` обязан соответствовать зарегистрированной закрытой схеме. Это не `any`: неизвестный контракт блокирует публикацию/команду. Конкретные схемы механик и визуальных профилей отдельно. |
| `QuantitySet` | `{coins: UInt, xp: UInt, family_contribution: UInt}` | Суммы исходного обещания. Для дельт используется отдельный тип со знаковыми `Int`. |
| `ActorContext` | `{account_id: EntityId, binding_id: EntityId, profile_id: EntityId, mode: Key}` | Серверный снимок инициатора/режима, не произвольный объект клиента. Технические фоновые действия используют отдельный тип service-инициатора. |
| `CauseRef` | `{operation_id: EntityId, source_type: Key, source_id: EntityId, effect_key: Key}` | Поддерживаемый тип исходной записи и конкретного эффекта. Источник неизменен; новый ключ HTTP не создаёт новый смысловой эффект. |
| `GoalBinding` | `{state: unbound}` либо `{state: bound_to_goal, goal_id: EntityId, bound_at: Instant}` либо `{state: bound_without_goal, bound_at: Instant}` | Неактуальные поля запрещены. После первой отправки `unbound` недопустим. Смена исполнителя не меняет адресат. |

В этой версии массивы обозначаются `List<T>`; порядок семантически значим только если указан. Множества — `Set<T>` с запретом повторов. `Enum(a,b)` — закрытый набор для конкретной версии контракта. Новые значения механик не появляются из произвольного пользовательского текста.

## 3. Общие поля и правила наследования

| Набор | Поля | Применение |
|---|---|---|
| `Identity` | `id: EntityId!`, `schema_version: SchemaVersion!`, `created_at: Instant!` | Все runtime-записи в словаре. Номер строки/порядок массива не заменяет ID. |
| `Mutable` | `state_revision: Revision!`, `updated_at: Instant!` | Изменяемые записи. Ревизия увеличивается при каждом изменении значимого состояния. |
| `FamilyScoped` | `family_id: Ref<Family>!` | Каждая семейная запись. Даже когда семья выводится через владельца, целевой контракт должен проверять согласованность всей цепочки. Физическое дублирование колонок решается отдельно. |
| `ProfileOwned` | `owner_profile_id: Ref<MemberProfile>!` | Владение, кошелёк, питомец, личный выбор. Не смешивать с `actor_profile_id` инициатора. |
| `ImmutableEffect` | `cause: CauseRef!`, `recorded_at: Instant!` | Зафиксированные начисления/списания/коррекции. Обычного `updated_at` и редактирования суммы нет; компенсация записывается отдельно. Обработка личных данных по L08 остаётся отдельной процедурой. |
| `Retention` | `retention_policy_id: Key!`, `retention_policy_revision: Revision!` | Классификация и применённая версия политики. Реестр содержит цель, категорию, момент начала отсчёта, срок/основание сохранения и процедуру удаления. Изменение обязательных правил требует переоценки существующих данных; старая ссылка не освобождает от новых требований. Значения срока до O01/O09 не выбраны; отсутствие срока не означает «вечно». |

Наборы — сокращение спецификации, а не требование наследования таблиц PostgreSQL. Каждая запись наследует только перечисленные наборы. Публичный ответ не является автоматической сериализацией всей внутренней записи.

## 4. Уникальность, обязательность и ограничения

| Проверка | Требование |
|---|---|
| Структура | Известный контракт/версия, обязательные поля, диапазоны, корректные даты, уникальные элементы множеств, условные поля. В канонических командах и авторском контенте лишние свойства отклоняются. Совместимость чтения старых клиентов задаётся явно через версии/проекции. |
| Ссылки | Тип и существование цели; точная ревизия; Family всех сторон; владелец предмета/слота; опубликованность и разрешённое использование. FK сам по себе не заменяет разрешение операции. |
| Бизнес-уникальность | Один settlement на исходную долю; один стартовый выбор на профиль; одна коллекционная позиция на владельца; одна активная награда конкретного предложения на ребёнка; однократная компенсация эффекта. |
| Согласованность | Покупка и владение; резерв и квота; приём дела и награды; BEN и обе стороны; доступ и отзыв. Все ограничения повторно проверяются при фиксации операции. |
| Версии | Опубликованная ревизия не изменяется на месте. Миграция связывает старый и новый контракт/ID, проверяет сохранения и имеет план восстановления. Право владения не исчезает из-за скрытия предложения. |
| Доступ/секреты | Роль/баланс/цена/инициатор вычисляются сервером. Полные PIN, токены и коды восстановления не включаются в журнал или DTO. Проверочные значения секретов не публикуются. |
| История | Источник, фактические условия и последствия сохраняются в пределах утверждённой политики данных. Переименование пользователя не меняет ID; удаление данных не обходится «вечным неизменным JSON». |

## 5. Покрытие и явные границы этой версии

Словари охватывают все именованные сущности разделов 4.1–4.4 DOMAIN_MODEL. Для каждой заданы общие наборы, поля, обязательность и ключевые ограничения. Дополнительные вложенные структуры описаны в своих словарях; состояние не заполняется демонстрационными записями.

Это полный перечень логических сущностей принятой модели, но ещё не окончательный wire-контракт каждой команды. Остаются: точные JSON Schema всех TypedPayload; детальная схема всех команд и серверных проекций; технические сроки/криптография; измеренные лимиты строк/файлов/коллекций; визуальные профили Asset Bible; правила выпусков; физические ограничения/индексы/миграции. Они перечислены явно и не считаются проверенными от наличия таблиц полей.

Особенно важно: резервирование квоты должно иметь собственную устойчивую запись/ключ на этапе физической схемы; нельзя восстанавливать прошлые лимиты только по текущим настройкам RewardOffer. Состав соглашения и период сохраняются в заказе. То же относится к снимку календаря и участникам совместного дела.

## 6. Основания выбора форматов

UUIDv7 стандартизован RFC 9562; здесь он предложен для runtime-ID, а не выбран в текущем коде. RFC 8259 описывает ограничение переносимой точности целых для широко используемых JSON-реализаций; десятичные строки выбраны нами для больших точных счётчиков. JSON Schema 2020-12 позволяет описывать структуру и условия, но не заменяет доменные проверки. Проверено 2026-09-07: [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7), [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html#section-6), [JSON Schema Validation](https://json-schema.org/draft/2020-12/json-schema-validation).

Конкретная библиотека UUID/валидации, SQL-типы и технические числовые пределы ещё не выбраны. Перед генерацией/приёмкой схем формат `date-time` должен проверяться действующим валидатором с нужным режимом, а не считаться доказанным одной аннотацией `format`.
