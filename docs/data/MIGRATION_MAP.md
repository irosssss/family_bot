# Family Chores RPG — инвентаризация кода и карта переноса

Версия 1.0, 2026-09-07. **Проект PDB06–PDB08 принят; правила переноса конкретных данных ещё не утверждены.** Согласование этой карты не запускает миграции и не выбирает реальные семьи/балансы для импорта. Целевая схема: [PHYSICAL_SCHEMA](PHYSICAL_SCHEMA.md); последовательность операций: [TRANSACTIONS](TRANSACTIONS.md).

## 2. Карта legacy-таблиц

Коды исхода: **M** — кандидат на перенос после проверки; **R** — требуется явное решение/сверка; **H** — отдельная историческая область без повторного исполнения; **D** — демо, не включать в production автоматически. Эти статусы не означают удаление исходных строк. Все runtime-ID через migration_id_map; serial не преобразуется в UUID математической догадкой.

## 3. Переиспользование кода

| Компонент / паттерн | Предлагаемое действие | Причина |
|---|---|---|
| React/Vite/Tailwind, UI primitives, mobile layout | Сохранить каркас, проверить экраны по новой матрице действий | Цель — развитие существующего приложения, не переписывание стека ради схемы. |
| Express routers / сервисные границы | Постепенно подключить target command/query adapters | Старые URL/body не должны обходить новый Account/Binding/SessionContext. |
| walletService условный debit + transaction | Переиспользовать паттерн, изменить модель и добавить reservation/ledger | Текущий users.gold не выражает reserved и историю обещания. |
| progressService effects / DB transaction | Использовать опыт атомарности, перепроектировать правила и хранение | Старый undo может отказать из-за spent balance/использованного pet; X требует ограниченную компенсацию с сохранением приобретений. |
| demo/store family-row locking | Переиспользовать идею сериализации локального агрегата | Целевой family lock работает с нормализованными таблицами; whole-world JSON не становится production-схемой. |
| Telegram validation adapter | Аудировать и адаптировать для проверенной ExternalIdentity | Не переносить dev fallback и family_code как целевой security protocol. |
| appState / большие state DTO | Постепенно заменить разрешёнными DB projections и инвалидируемыми кешами | Клиенту ребёнка не отправляется всё состояние с последующим скрытием полей. |
| src/data/initialData.ts, src/demo/catalog.ts, визуальные mapping в коде | Выделить принятый контент в versioned данные после Asset Bible | Код не должен оставаться единственным каталогом основной графики и цен. |

Это карта предполагаемого использования, не разрешение сейчас удалять старые функции или менять runtime. Legacy и demo продолжают работать в своих текущих границах до отдельно разрешённого перехода.

## 4. Таблицы технического переноса

Новые таблицы предлагаются в rpg, с ограниченным доступом и утверждённой политикой хранения. Они не создаются этой документацией.

| Таблица | Поля и ключи | Инвариант |
|---|---|---|
| migration_runs | id uuid PK, lineage_run_id uuid FK → migration_runs(id), source_system text, source_snapshot_ref text, source_schema_digest, target_contract_version, mapping_version, scope_manifest_ref, state, started_at, finished_at nullable, R | Первый run ссылается на себя, последующие — на его id: повтор не создаёт новую область соответствий. Состав/версии источников воспроизводимы; секреты подключения не записываются. |
| migration_id_map | id uuid PK, lineage_run_id uuid FK → migration_runs(id), source_system, source_entity, source_key text, target_kind, target_id uuid nullable, target_content_id text nullable, resolution_state, decision_ref, R | U(lineage_run_id,source_system,source_entity,source_key,target_kind). У resolved ровно один вид target ID; у unresolved оба null. Повтор использует прежний target; один legacy users может иметь несколько target kinds. |
| migration_records | id uuid PK, run_id, F nullable для ещё неразрешённой семьи, source_entity/key, source_digest, disposition, mapping_revision, evidence_ref, approved_by_ref nullable, approved_at nullable, applied_operation_id nullable, R | disposition pending/approved/applied/quarantined/excluded. Только approved вызывает целевые effects. Payload персональных исходников не дублируется бессрочно в audit. |
| migration_reconciliations | run_id, check_key, scope_key, expected_value text, actual_value text nullable, result, evidence_ref, checked_at, R; PK(run_id,check_key,scope_key) | Exact суммы как decimal string, проверяемые counts/digests; expected неизвестно → unresolved, не PASS. |
| family_storage_routes | family_mapping_id uuid PK, authoritative_store enum legacy/target, route_revision integer, cutover_run_id nullable, switched_at nullable | Одна точка записи для семьи; old endpoint/cron читает актуальный route или блокируется. Не допускает скрытый dual-write. |

Source snapshot должен иметь отдельный ограниченный storage/retention scope. Обычный экспорт семьи не включает чужие сведения migration staging. Идентификаторы source/target могут связывать личность и не считаются обезличенными автоматически.

Для imported OwnedPet предлагается `origin_kind=approved_import` + import_record_id вместо выдуманной EggAcquisition. Для обычного нового питомца остаются исходные egg-поля/бесплатное вылупление. Начальный остаток кошелька — отдельный ledger effect с source migration_record и стабильным effect_key, а не пользовательское выполнение задачи. Импорт старой истории не запускает eligibility/start bonuses/голосование/рассылку автоматически.

Стартовое право уже игравшего ребёнка — отдельное решение mapping: наличие старого pet или gold само не доказывает, что он использовал новую StarterPetChoice. Его нельзя молча отметить выбранным/невыбранным. Такая запись остаётся нерешённой до принятия политики сохранения старого прогресса.

## 5. Последовательность перехода

| Шаг | Результат | Условие перехода |
|---|---|---|
| M0 — проект, текущий этап | Таблицы, ограничения, карта источников и неизвестных | Приёмка PDB, решение зависимых правил. Никаких операций БД. |
| M1 — разрешённая инвентаризация | Схема/версии/индексы, минимальные агрегаты целевых источников | Явно выбранная среда и область чтения; не предполагать, что локальная БД пуста. |
| M2 — политика соответствий | Какие профили/средства/права сохраняются; зоны/roles, pending rewards, starter status, art mapping | Неразрешённые строки не считаются успешно перенесёнными; согласованные исключения перечислены. |
| M3 — изолированная сборка | DDL/Drizzle и синтетические fixtures, constraint/transaction tests | Отдельное разрешение на реализацию. Проверки на новой тестовой БД, не на рабочей семье. |
| M4 — staging / dry run | Source snapshot, id_map, transformed records без доступа клиентов | Dry run не вызывает игровые команды и не пишет ledger рабочего продукта. Проверки FK/ownership/остатков. |
| M5 — rehearsal восстановления | Восстановление копии, повтор импорта, сверка, пробный cutover | Повторные ID/эффекты совпадают; протестированы failure paths, отсутствуют двойные бонусы. |
| M6 — ограниченный cutover | Для выбранной семьи остановлены все legacy writers, финальная сверка и target route | Согласованное окно без записи: HTTP, бот, cron, фоновые jobs также остановлены/ограждены. Снимок не устаревает во время переноса. |
| M7 — приёмка целевого состояния | Разрешённые экраны/балансы/коллекции, новые операции работают, ledger сверяется | Нет unresolved записей в обещанном объёме; результаты проверены пользователем, доступ реально переподтверждён где требуется. |
| M8 — завершение перехода | Legacy становится ограниченным read-only архивом на принятый срок | Удаление старой копии отдельным процессом данных; не выполнять DROP только из-за успешного логина. |

Первый вариант — короткое согласованное окно без записи, без сложного CDC/двойной записи. Время окна нельзя оценить без реальных размеров и dry-run. Если окно неприемлемо, нужна отдельная схема delta capture/replay и новый аудит; не обещать «нулевой downtime» текущим планом.

## 6. Что означает откат

До открытия target для новых действий можно вернуться к неизменённому legacy route и удалить только явно разрешённые staging/target-копии этого run. Верификация должна подтвердить, что ни одно внешнее обязательство не возникло.

После хотя бы одного нового target commit старый снимок уже устарел. Простой возврат маршрута потеряет покупки/выполнения. Тогда сначала ограничить запись, сохранить журнал новых операций и либо исправить target вперёд, либо выполнить заранее проверенный обратный перенос с полной сверкой. Перезапуск старого server.ts может снова выполнить catalog initialization; один switch UI не является безопасным rollback.

Бэкапы и source snapshots также включаются в карту удаления. Повторный импорт из прежнего снимка обязан учитывать удаления после даты снимка, иначе удалённые профили/имена вернутся. Сроки хранения и правила suppression должны быть утверждены до работы с реальными данными.

## 7. Обязательная сверка перед приёмкой переноса

| Проверка | Ожидаемый результат |
|---|---|
| Полнота источника | Каждая исходная строка выбранной области имеет disposition; нет пропавших без объяснения строк. |
| Идентичность | Source→target mapping устойчив при повторе; нет автоматически действующих synthetic Telegram identities. |
| Семья / роль | Все связанные записи одной семьи; parent не получил игровой wallet по умолчанию; нет семьи без допустимого взрослого. |
| Деньги / XP | Exact opening totals соответствуют принятому источнику; ledger=cache; исторические события не начислены второй раз. |
| Владение | Сохранены все отдельно утверждённые права; slots/collection_keys без конфликтов; неизвестный asset не заменён случайным. |
| Реальные награды | Для каждого переносимого обязательства подтверждены цена/возврат/состояние; купленное не объявлено выданным без основания. |
| Даты | Исходные моменты/семейные дни и неопределённые зоны разрешены явно; NOW не подменяет историю. |
| Питомцы | Нет дубликатов egg/pet claim; каждый импортированный pet имеет происхождение и базовый corner; новое стартовое право не выдано автоматически. |
| Старые коммерческие данные | Нет повторного credit платежа/реферала; судьба подтверждённых прав имеет отдельное решение. |
| Повтор / сбой | Повтор run не меняет target ID и не удваивает эффекты; прерванный cutover не оставляет двух writers. |
| Демо-графика | Все включения в целевой каталог явно маркированы и разрешены; нынешние картинки не получили статус основных автоматически. |

## 8. Границы реализации мигратора

Существующие `db:push` и `db:migrate` — разные механизмы, запускать их вперемешку для production-перехода нельзя. Предлагается один reviewable SQL migration journal, генерация Drizzle как подготовка проверяемого SQL, ручная проверка сложных constraints/triggers. В будущей доработке журналу нужны checksum содержимого и глобальная блокировка запуска migrator, чтобы два процесса не применяли один файл одновременно. Существующий baseline нельзя переписать задним числом без аудита.

Исторические `DAT-01 FIX`/`DAT-02 FIX` в комментариях кода относятся к прежнему аудиту; это не текущие проектные решения DAT01–DAT08. Названия похожи, но статусы и происхождение разные.

Следующий результат после приёмки PDB — Asset Bible и UX-контракт по roadmap; нерешённые QDB01, security/retention и конкретные import dispositions сохраняются как зависимости до реализации. Основные ассеты ещё не создаются. Контентная и визуальная работа может идти на синтетических примерах без доступа к реальным семейным записям.
