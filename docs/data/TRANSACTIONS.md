# Family Chores RPG — транзакции, конкурентность и сверка

Версия 1.0, 2026-09-07. **Проект PDB04–PDB05 принят вместе с [физической моделью](PHYSICAL_SCHEMA.md); QDB01 остаётся открытым отдельно.** Продуктовые правила остаются в [контракте](../PRODUCT_CONTRACT.md). Здесь описана целевая реализация; это не результаты выполненных нагрузочных/интеграционных тестов.

## 1. Единый порядок мутации

1. Разобрать закрытую схему команды и проверить базовую идентичность. Клиентские actorId/role/price не являются полномочиями или источником суммы.
2. Начать транзакцию READ COMMITTED. Для глобального изменения identity сначала блокировать необходимые Account по отсортированным UUID. Обычная семейная команда не блокирует Account на запись, но проверяет актуальность identity после получения семейной блокировки.
3. Взять `SELECT ... FOR UPDATE` строки `rpg.families` целевой семьи. Для разрешённого административного процесса нескольких семей — заранее определить область и брать семьи в одинаковом порядке UUID. Игровые команды MVP не переносят эффекты между семьями.
4. Повторно проверить привязку/сессию/режим, active/archived, PIN freshness, получателя и ожидаемые ревизии. Отзыв привязки также берёт эту семейную блокировку, поэтому покупка и отзыв получают определённый порядок.
5. Прочитать receipt в области principal + family + command + key. Тот же ключ и тот же digest возвращают авторизованное представление сохранённого результата; другой digest → conflict без эффектов. Очистка receipt не снимает бизнес-ограничения источника.
6. Проверить источник действия, точные условия и бизнес-уникальность; при необходимости заблокировать mutable глобальное предложение после семьи. Публикация контента не берёт семейные блокировки в обратном порядке.
7. Записать operations, source/effect records, дочерние записи, обновлённые проекции и receipt в одной транзакции. Проверить отложенные FK/constraint triggers. Любая ошибка откатывает весь набор.
8. После commit вернуть DTO и инвалидировать разрешённые кеши/уведомления. Изменение appState до commit не является источником истины. Ошибка отправки уведомления не повторяет начисление.

Внутри семьи все целевые writers, включая фоновые генераторы, исправления и выдачи, обязаны следовать одному протоколу. UNIQUE и FK остаются последним барьером при ошибке кода. Прямые writes из старых API в новые таблицы не допускаются. Для принудительного соблюдения границ у приложения нет прав DDL/изменения схемы; способы ограничения ledger writes закрепляются при создании роли и командного слоя.

`READ COMMITTED + family lock` — осознанный вариант MVP, а не автоматическая serializable-гарантия любых запросов. Глобальное disable Account должно сначала заблокировать Account, затем все его затрагиваемые семьи в том же порядке и инвалидировать сессии до commit; если такой fan-out неприемлем по измерениям, потребуется отдельный принятый протокол revocation epoch. Нельзя молча отключать только кеш Account и обещать атомарный отзыв во всех семьях.

Запрос полного экрана читает согласованную проекцию одним SQL-запросом либо read-only REPEATABLE READ-транзакцией, если нужны несколько запросов одного снимка. Блокировку семейной строки не держат во время сетевых запросов, рендера, генерации файлов или ожидания согласия человека.

## 2. Операции и постоянная уникальность

| Операция | Что коммитится вместе | Постоянный барьер повторов |
|---|---|---|
| Открыть плановое выполнение | occurrence, frozen terms/calendar, allocations, source record | U(F,definition_id,local_date), U(occurrence_id,share_index). Новая revision задания не создаёт второе дело того же планового дня. |
| Отправить выполнение | attempt, статус allocation, первый goal_binding всего occurrence | Один submitted на allocation. Unbound меняется только один раз под общей блокировкой. |
| Принять результат | accepted attempt/decision, единственный settlement, coins/XP/contribution effects, caches, стартовое право при первой допустимой награде | U(allocation_id), семантические initial effect keys, U(F,P) starter choice. Новый HTTP key не выдаёт награду повторно. |
| Купить виртуальный предмет | quote snapshot, purchase, debit, entitlement/egg claim, receipt | U(F,P,ownership_key) либо U(F,P,collection_key), плюс операция покупки. Конфликт выдачи откатывает списание. |
| Запросить реальную награду | order snapshot, money reservation, quota claims | Один незавершённый order предложения на ребёнка; уникальная claim bucket/order. |
| Купить гарантированную награду | order, debit, quota claims | Те же ограничения заказа/квот, без промежуточного денежного резерва. |
| Одобрить реальную награду | decision, reservation capture, единственный debit, order purchased | Capture terminal transition; исходная цена и квотный период, не новая версия offer. |
| Отклонить/отменить запрос | decision/order, release денежного резерва и всех held quota claims | Однократный release; второго «возврата денег» при простом снятии резерва нет. |
| Семья не может выдать купленное | refund effect на невозвращённый фактический расход, order refunded, release квот | Сумма всех возвратов ≤ исходному debit. Нет произвольного возврата по нынешней цене. |
| Отметить получение / исправить отметку | fulfillment decision/history, order state, held↔consumed quota | Нет нового debit/refund. Исправление возвращает previous_order_status. |
| Выбрать стартовое яйцо | choice chosen, exact option, acquisition, collection claim | Один выбранный starter choice и один collection claim. |
| Вылупить яйцо | acquisition hatched, pet, бесплатный corner, claim связь | Один pet на acquisition/claim; двойной запрос не создаёт второго питомца/уголка. |
| Выбрать внешний вид/спутника | совместимые выбранные FK, state_revision | Один target/slot, один ActiveCompanion; у детского режима только свой профиль. |
| Достичь семейной цели | contribution, current_amount, achieved, unlock | Одна active цель на семью; U(F,unlock_key), повтор достижения не выдаёт улучшение дважды. |
| Исправить начисление | case, реально допустимые компенсации, waived, caches, история | Проверка некомпенсированного остатка исходного эффекта и уникального case/phase/effect. Нет отрицательных available coins. |
| BEN A→B / undo | обе стороны coins/XP, attribution contributions, settlement/allocation current recipient, cases и сохранённые права | Один применённый перенос и одна отмена на allocation MVP; исходная цель/доля сохраняются. |
| Отозвать/восстановить доступ | bindings, protection revision, recovery material, sessions/invites/ограниченные grants | Область конкретного взрослого этой семьи; одноразовые credentials/requests и повторная проверка прав. |
| Архив / возобновление | актуальные согласия, повторная проверка незавершённых обязательств, family status | Membership_revision и полный состав взрослых; ни одного автоматического согласия по таймеру. |

Команда с отклонёнными условиями может сохранить rejected receipt без игровых эффектов отдельным согласованным выходом той же транзакции. Ошибка SQL не превращается в committed receipt. Соединение оборвалось после возможного commit → клиент повторяет исходную команду с тем же ключом; сервер определяет результат по receipt/semantic source. Технические retries deadlock/serialization ограничены политикой сервера; точные число/тайминги выбираются по нагрузке, не фиксируются выдуманным SLA.

## 3. Денежный журнал и пересчёт

| Величина | Источник истины | Проверяемая проекция |
|---|---|---|
| Posted coins | Сумма wallet_entries.delta, включая отдельно утверждённый импортный opening effect | wallets.posted_balance |
| Reserved coins | Сумма amount у reservations со status=active | wallets.reserved_balance |
| Available coins | Posted − reserved | Вычисляется; ≥0 всегда, сумма резервов ≤ posted. |
| XP | Сумма xp_delta progress_grants | player_progress.xp; уровень по отдельной принятой версии таблицы уровней. |
| Вклад цели | Сумма goal_contributions.delta, закреплённых за ней | family_goals.current_amount; величина не ограничивается target сверху. |
| Потребление квоты | Held + consumed claims исходного bucket | Вычисляется под lock либо кеш с обязательной сверкой. |
| Постоянное владение | owned_entitlements/pet_collection_claims/house_unlocks | Внешний вид — выбор ссылок, не показатель наличия покупки. |

При ошибке начисления `recoverable = min(неисправленная ошибочная сумма, available)`. Разница записывается waived и больше не взыскивается из будущих доходов. Резервы не отнимаются, покупки не удаляются. Восстановление возвращает только applied исходной коррекции. Расхождение кеша с журналом блокирует новую операцию затронутого кошелька и создаёт диагностику; «исправить баланс по памяти» недопустимо.

Контрольный пример принятого BEN: A ошибочно получил 20 монет, доступно 6. Применение A−6, waived14, B+20. Если при отмене у B доступно только 8: B−8, waived12, A+6. Итоговая дополнительная денежная масса здесь ожидаема по X09–X16, а семейный вклад не удваивается. Сверка сравнивает журнал с этими эффектами, а не требует ложного нулевого суммарного переноса.

Независимая периодическая сверка сравнивает проекции с SUM без повторного исполнения игровых команд. Частота и операционные пороги будут выбраны после измерений. Верификатор не вносит корректирующие записи сам без подтверждённого основания/процедуры.

## 4. Периоды квот и изменение календаря

Для каждого заказа сохраняются исходные правило, величина лимита и bucket. Дневной bucket относится к семейному дню, недельный — к неделе с понедельника; одобрение в следующей неделе продолжает использовать прежний bucket. Смена цены/текста не создаёт новый rule_key и новую квоту. Новая независимая политика лимита требует явного отличия от косметической ревизии предложения.

Остаётся конкретное зависимое решение **QDB01**, которое нельзя подменять SQL-индексом: точный момент применения новой зоны/нового размера лимита к ещё открытым учётным периодам. Предлагаю сохранять активный bucket и его границы до завершения; новые границы вычислять после него без перекрытия/повторной выдачи квоты. Уменьшение лимита не отменяет уже созданные обещания; новая покупка при исчерпании не проходит. Это предложение поведения перехода, а не ранее подтверждённая продуктовая политика. До отдельного решения этого пункта соответствующие команды изменения зоны/лимитов не считаются готовыми к DDL/реализации.

Для total-лимита фиксированный period_key=lifetime. Bucket scope family требует NULLS NOT DISTINCT либо эквивалентных двух частичных индексов, иначе nullable profile допускает дубликаты. Решение физического проекта — NULLS NOT DISTINCT для целевого PostgreSQL 18; фактическая версия БД всё равно проверяется перед применением.

## 5. Согласованность с версиями и выход из транзакции

Редактор выпускает неизменную content revision и её нормализованные зависимости одним commit. Активация release — отдельная команда, которая сначала проверяет полноту файлов, схем и поддерживаемых capabilities. Клиент получает точный manifest, а не смесь current pointers из разных моментов. Подмена демо-файла по прежнему storage_key не является допустимым обновлением.

Если понадобятся гарантированные фоновые уведомления, их намерения фиксируются в outbox той же транзакцией, worker повторяет доставку с собственным ключом. Это предложение технического механизма, не включение новых рассылок или разрешение отправлять сообщения. До принятия канала/требований можно ограничиться ответом API и инвалидируемой проекцией. Ошибка сети никогда не удерживает family lock.

## 6. Будущие проверки на швах

Каждая строка — спецификация будущего интеграционного теста на реальной изолированной PostgreSQL, **не уже выполненный тест**.

| ID | Одновременные действия / отказ | Ожидаемое доказательство |
|---|---|---|
| DBT01 | Два открытия одного дела разными process/key | Один occurrence, исходные доли и только одна snapshot revision. |
| DBT02 | Два принятия одной allocation с разными request keys | Один settlement, один набор initial effects и одна стартовая eligibility. |
| DBT03 | Покупка и расход в другой вкладке | Posted/reserved/available неотрицательны; только допустимые приобретения. |
| DBT04 | Два запроса последней квоты | Только один claim/заказ проходит, у отказавшего нет списания/резерва. |
| DBT05 | Одобрение и отмена одного reserve | Либо capture, либо release; не оба эффекта, сумма согласована с order. |
| DBT06 | Падение после debit до entitlement | Нет ни покупки, ни списания после rollback. |
| DBT07 | Потерян ответ после commit | Повтор возвращает сохранённое право без второго начисления/расхода. |
| DBT08 | Два вылупления, покупка второго яйца той же позиции | Один claim/pet/corner, повторная покупка отклонена до эффекта. |
| DBT09 | Совместное дело: разные доли до/после смены active goal | Все доли сохраняют binding первого submit. |
| DBT10 | BEN и расход A/B | Ограниченная компенсация, B получает обещанное, общая цель не удваивается. |
| DBT11 | Отмена BEN после расхода B | Возвращено A только ранее applied; waived не превращено в долг. |
| DBT12 | Отзыв сессии и покупка | Один разрешённый порядок; после отзыва новые операции через неё не проходят. |
| DBT13 | Изменился состав взрослых до архива | Старые consents не дают архив; последний взрослый не выходит. |
| DBT14 | Через SQL передан FK другой семьи/владельца | Соответствующий composite FK отклоняет запись, не только HTTP guard. |
| DBT15 | Очистка transport receipts и повтор source | Повтор награды блокирует постоянная бизнес-уникальность. |
| DBT16 | Рассогласована wallet/XP projection в fixture | Диагностика выявляет отличие без автоматического повторного начисления. |
| DBT17 | Выпущен пакет с несуществующей revision/несовместимым slot | Блок активации; действующий release и приобретённая графика остаются разрешимыми. |
| DBT18 | Импорт запущен повторно | Те же target ID/effects, ни нового стартового подарка, ни второго opening balance. |
| DBT19 | Бэкап восстановлен после удаления данных | Deletion suppression применяется до открытия чтения; данные не возвращаются через импорт/legacy. |
| DBT20 | Предельные bigint, дробное число, timestamp с зоной | Exact roundtrip; недопустимое отклонено до SQL-приведения; нет округления через Number. |

Порядок блокировок и их время жизни сверены с [PostgreSQL 18 Explicit Locking](https://www.postgresql.org/docs/18/explicit-locking.html). Сам выбор одной семейной блокировки — проектное решение для данного MVP. Производительность и отсутствие deadlock в реализации нужно доказать тестами, а не ссылкой на документацию СУБД.
