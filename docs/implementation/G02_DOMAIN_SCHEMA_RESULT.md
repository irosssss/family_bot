## 1. Результат и границы

В собственной временной PostgreSQL созданы пять таблиц. Игрок ссылается на детский профиль конкретной семьи: неверную роль или чужую семью отвергает сама БД. У родителя не появляется игровой счёт. Account и семейный профиль остаются разными сущностями; доступ между ними будет оформлен в G03.

| Таблица `rpg.*` | Реализованные поля | Основные ограничения |
|---|---|---|
| `retention_policy_revisions` | policy_id, revision, purpose, category, trigger, schema_version, policy_payload | Составной PK версии, ключи ASCII snake_case с collation C, закрытый JSON-конверт; значение проверяет зарегистрированный parser. |
| `accounts` | I/M/R; status, disabled_at | UUIDv7, поддержанная схема 1, положительная ревизия, конечные согласованные даты, status active/disabled/erasure_pending. Нет family role/кошелька. |
| `families` | I/M/R; display_name, status, zone_id, calendar_revision, membership_revision, recurrence_paused, recurrence_paused_at, archived_at, last_resumed_at | Независимые положительные ревизии, согласование паузы/архива с датами, обязательный FK на версию retention. |
| `member_profiles` | I/M/F/R; display_name, family_role, status, archived_at, left_at | Family FK, U(family_id,id), U(family_id,id,family_role), parent/child, состояния active/archived/left; индекс семейного списка. Имена могут совпадать. |
| `players` | I/F/R; profile_id, role | Только child; составной FK (family_id,profile_id,role), U(family_id,profile_id), U(family_id,id). Не дублирует Account/аватар/XP/кошелёк. |

I = id/schema_version/created_at; M = state_revision/updated_at; F = family_id; R = retention_policy_id/retention_policy_revision. Все ссылки retention обязательны. Даты хранятся как timestamptz(3); адаптер нормализует их в UTC с миллисекундами. Defaults «сейчас» и случайные сроки хранения не добавлены.

## 2. Уточнения и найденные расхождения

1. **Исправлен дефект G02-A в диапазоне Int.** Принятый PDB требует симметричного диапазона −9223372036854775807…9223372036854775807. Старый parser ошибочно принимал −9223372036854775808, которое нельзя безопасно отрицать в SQL bigint. [Parser](../../src/target/contracts/numbers.ts) и граничный тест исправлены по существующему требованию. Это исправление реализации, не смена экономики или спецификации.
2. **Детерминированный порядок DDL.** Первый прогон обнаружил разный порядок CREATE TABLE при перечислении экспортов native ESM и Vitest. Введён явный объект foundationSchema. Итоговые байты SQL одинаковы в генераторе и тесте; схема БД от этого не менялась.
3. **Трактовка nullable timestamps закреплена явно.** Active Account имеет disabled_at=null; disabled требует дату; erasure_pending допускает отсутствие прежнего отключения. У профиля даты показывают текущее состояние и очищаются при смене состояния; полная история относится к будущим lifecycle-записям. Семья может сохранять archived_at после возврата как последнюю дату архива. recurrence_paused_at — дата действующей паузы, null при снятой паузе. Событие не позже updated_at и не раньше created_at. Полные переходы, история и увеличение ревизий реализуются командами последующих этапов.
4. **Политики не подменены тестовыми сроками.** В миграции нет seed-политики. Fixtures используют только fixture_retention с действием delete_with_test_database. O01/O09 не закрыты; реальный обработчик хранения и контроль неизменности опубликованных политик остаются последующим этапам.

Drizzle `$type` не обеспечивает runtime-валидацию. Поэтому SQL проверяет конверт JSON, а приложение требует явный реестр parser-ов для value; неизвестная пара contract_id/schema_version отклоняется. Источники технической сверки: [официальные типы PostgreSQL в Drizzle](https://orm.drizzle.team/docs/column-types/pg), [ограничения Drizzle](https://orm.drizzle.team/docs/indexes-constraints) и установленный исходник drizzle-orm/postgres-js/driver.js. Фактическое поведение дополнительно проверено на локальных установленных версиях, без обновления зависимостей.

## 4. Предел результата и следующий шаг

G02 выполнен в базовом объёме W04–W07. Доменные таблицы контента, операций/кошельков и полного жизненного цикла добавляются в своих этапах. Полные DBT/CPT/VQA не считаются пройденными этим набором.

Составные FK защищают целостность связей, но **не заменяют авторизацию чтения и команд**. Target пока имеет только health/readiness; readiness проверяет свою БД, не готовность всей игровой схемы. У него нет семейных API, сессий, PIN, recovery или реальных данных. UI, ассеты, прежний runtime, его таблицы и журнал миграций не изменялись этим этапом. Новый код не подключён к прежнему приложению.

Проверка зоны использует базу Intl текущего Node; пользовательские ограничения длины имён и согласованность timezone-адаптеров должны быть закреплены до публичного API G03. Прямой SQL не проверяет IANA-реестр или payload registry. Monotonic revision/CAS, минимально необходимые права DB-роли, запрет переписывания retention-версий и протоколы архивирования остаются обязательствами соответствующих сервисов до работы с настоящими семьями.

На момент завершения G02-B следующим согласованием был [G03-A](G03_ACCESS_PROTOCOL_CARD.md); затем он разрешён и подготовлен к приёмке. Карточка разрешает сначала проверяемую спецификацию, а не преждевременное подключение детей или назначение непроверенных сроков/политик.
