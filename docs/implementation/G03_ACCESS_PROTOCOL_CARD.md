# G03-A — спецификация доступа и границ безопасности

Версия 1.0, 2026-09-07. **Разрешено сообщением «дальше давай» после G02-B; спецификация подготовлена к приёмке.** Основа: [G02-B](G02_DOMAIN_SCHEMA_RESULT.md), A01–A16 [продуктового контракта](../PRODUCT_CONTRACT.md), логическая модель доступа DAT/PDB. Уточняет W08; код авторизации W09 и последующие работы требуют следующей конкретной карточки.

## 1. Результат этапа

Один согласованный технический протокол для собственного Telegram-входа ребёнка и управляемого доступа через взрослого. Оба ведут к прежнему семейному профилю и будущему единственному кошельку/коллекции. Протоколы оформляются как состояния, команды, обязательные проверки, отказы и тестовые сценарии.

| ID | Работа | Проверяемый результат |
|---|---|---|
| G3A01 | Сверить правила Telegram Mini Apps и существующий helper с официальными источниками/независимыми примерами. | Точный способ проверки initData, freshness/replay, различие verified identity и семейных прав. Совпадение собственного генератора и validator не считается независимым доказательством. |
| G3A02 | Разделить Account, ExternalIdentity, MemberProfile, AccessBinding и Session. | Матрица «кто — какая семья — какой профиль — какое действие»; actorId клиента не доказывает права. |
| G3A03 | Описать собственный детский вход и приглашение в существующий профиль. | Одноразовость, проверенный кандидат, одобрение взрослого, идемпотентность и конкурентные подтверждения; без данных семьи до одобрения. |
| G3A04 | Описать общий девайс, личный шестизначный PIN взрослого и переключение. | Детская сессия не наследует взрослые действия; смена ребёнка/взрослого требует подтверждения; свежее подтверждение для чувствительных операций. |

## 2. Разрешаемая область

Чтение текущих исходников и принятых документов, проверка официальных технических источников, локальная документация и синтетические примеры без реальных учётных данных. Продуктовые A01–A16 не пересматриваются молча; обнаруженное противоречие предъявляется отдельно с конкретным вариантом решения.

Никаких сообщений пользователям/ботам, ввода реального PIN, регистрации настоящих детей, передачи initData внешним сервисам, подключения реальных семей или записи в их БД. Реализация API, новые секреты и миграции доступа не входят в G03-A.

## 3. Контрольная точка

G3A01–G3A08 оформлены в [протоколе доступа](../security/ACCESS_PROTOCOL.md), [параметрах SP01–SP17 и матрице GAT01–GAT24](../security/ACCESS_VALIDATION.md). Подготовлена [карточка G03-B](G03_IDENTITY_ADAPTER_CARD.md). Синтетическая проверка выявила расхождение канонизации legacy-validator; реальные Telegram-данные не использовались. Параметры остаются предложениями, GAT не исполнялись, runtime и БД не менялись.

Результат содержит: спецификацию протокола, таблицу параметров с основаниями, матрицу тестов, список действительно блокирующих вопросов и конкретную карточку G03-B. Вопросы O01/O09 запрашиваются только там, где ответ влияет на зависимое решение; пока ответа нет, документ сохраняет явную границу неопределённости. Приёмка G03-A не означает готовность входа или запуск MVP.
