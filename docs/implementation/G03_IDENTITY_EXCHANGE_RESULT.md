## 2. Почему добавлена служебная policy-таблица

Удалённый receipt нельзя восстановить, поэтому увеличение freshness после cleanup могло бы снова разрешить уже использованный вход. Храним постоянную границу активной политики: окружение/бот, digest настроек и ключа, ревизию и минимальный auth_date. Это необходимое уточнение карточки G3C05, а не хранение политики в памяти одного процесса.

| Операция | Гарантия |
|---|---|
| activatePolicy(expectedRevision) | Явная служебная операция; нет автоматической установки при startup. CAS/блокировка, новая verification revision для изменённой конфигурации, монотонное время и новый cutoff. |
| Смена ключа / окна / retention-конфигурации | Меняет канонический digest. Старый процесс получает policy_mismatch. Значение ключа в БД не хранится. |
| Смена среды/бота в уже используемой БД | Отказ deployment_mismatch. Тестовые и настоящие Telegram ID не смешиваются. |
| cleanupReceipts | Удаление строго после cleanup_after. Под exclusive lock сначала сохраняется временная граница в той же транзакции; возврат часов назад не оживляет забытый вход. |
| Одновременные обычные обмены | Shared policy-lock; advisory transaction-lock только по subject. Разные субъекты не сериализуются одним глобальным exclusive lock. |

Порядок блокировок обмена: policy(shared) → subject advisory → external identity(update) → account(share). Смена policy и cleanup используют exclusive policy-lock. Последующие команды отзыва обязаны учитывать этот порядок; семейные команды и их гонки ещё относятся к G03-D/E.

Технические границы реализации обмена: freshness не более 24 часов, clock skew не более 300 секунд, launch TTL не более 24 часов. Это предохранители конфигурации, не production-значения. Проверенная fixture policy: freshness 300 секунд/допуск30, 16 KiB/64 поля, launch10 минут. Retention задан по отдельной ссылке для account/identity/launch/receipt/policy; все тестовые ссылки ведут к удалению вместе с временной БД. O01/O09 остаются открытыми.

## 4. Что ещё не реализовано

Нет публичного auth endpoint, семейной SessionContext, PIN, приглашений/recovery, выдачи управляемого детского доступа или подключения нового ядра к UI. Resolver возвращает ограниченную внутреннюю проекцию, а не клиентский объект доказанных семейных прав. GAT06 закрыт на уровне сервис/БД; GAT07 — только отсутствие семейных полномочий у launch. Остальная сквозная матрица остаётся будущей.

Cleanup реализован для replay receipt. Удаление истёкших launch/identity/account, законные retention-сроки, production DB-роли, аудит оператора policy и публичные rate limits — последующие зависимые работы. Блокировки/тесты целостности не защищают от произвольного SQL суперпользователя. Не заявляется production-готовность входа.
