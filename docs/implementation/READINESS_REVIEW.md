# G01 — аудит готовности существующего проекта

Версия 1.1, 2026-09-07. **W01–W03 выполнены как локальный аудит и приняты пользователем.** Пользователь затем разрешил G02-A сообщением «делай»; [результат реализации](G02_FOUNDATION_RESULT.md) готов к приёмке. Ниже сохранены факты и границы именно аудита G01; его формулировки о непроведённых проверках относятся к моменту аудита. Основа: [план](../IMPLEMENTATION_PLAN.md), [backlog](../IMPLEMENTATION_BACKLOG.md), [карточка G02-A](G02_FOUNDATION_CARD.md).

## 1. Вывод

Целесообразно развивать существующий репозиторий с отдельной точкой входа целевой системы и явным внедрением зависимостей. Полезны геометрические алгоритмы, организация некоторых транзакций и отрицательные тестовые сценарии. Нынешние domain/state, каталог в TypeScript, доступ и хранение demo не соответствуют принятой целевой модели целиком. Механическое переименование типов или копирование demo JSONB не решает переход.

Основной первый риск — подключить новый код к старому bootstrap или неявно выбранной БД. Поэтому первая конкретная реализация предлагается как G02-A: изоляция, примитивы контрактов и независимый тестовый каркас. Базовые доменные таблицы G02-B следуют после проверки этой границы; G02 целиком до них не считается завершённым.

Это ограниченный аудит архитектурных швов, не построчное ревью всего репозитория. Связи ниже ссылаются на просмотренные файлы/символы; утверждение «не найдено» ограничено указанной областью поиска. Внешние спецификации, лицензии и версии инструментов в этом локальном этапе повторно не исследовались. Протокольная совместимость требует независимой проверки до переноса соответствующего кода.

Снимок исходников содержит **22 объявления pgTable** в [schema.ts](../../src/db/schema.ts), **17 файлов `*.test.ts`** в tests. `demo_worlds` создаётся SQL отдельно и не является ещё одним pgTable в этом файле. На момент аудита отсутствуют `src/target`, `content-source`, `content-build`, `art-source`; наличие PIPE-документов не означает готовности CLI. Ссылка `@RTK.md` в пользовательских инструкциях не разрешилась в локальный корневой файл; базовые AGENTS и память доступны.

Зафиксирован SHA-256 перечня байтов 173 файлов src/tests/scripts/migrations и выбранных root-конфигураций: `f7dc879738df31c1f7020151b151e7df1501460ef524fadb91dfed5a3d340783`. Это контроль неизменности локального кода в этом проходе, не git commit и не подпись/полный снимок всех файлов проекта. Документы и assets в этот перечень не включены; никакой визуальный вывод из него не делается.

## 4. Реестр значимых расхождений

| ID | Доказательство / статус | Последствие | Где устранить |
|---|---|---|---|
| RD01 | server.ts запускает DDL/seed/backfill/cron перед listen; подтверждено чтением. | Обычный dev-start не является чистой read-only проверкой. | G02-A отдельный bootstrap и тестовый config; старый сервер в G01 не запускался. |
| RD02 | Глобальный DB client с dotenv, отсутствие явного target/test guard; подтверждено. | Нельзя считать тест безопасным только из-за слова test в имени файла. | G02-A отдельные task-specific параметры, без legacy fallback, disposable DB и проверка назначения. |
| RD03 | В isAuthEnforced non-production или DEMO_MODE обходят guard; подтверждено, не вывод о фактическом deployment. | Такой режим нельзя наследовать новым семейным API. | G03 fail-closed target auth; G02-A пока вообще не регистрирует игровые маршруты. |
| RD04 | Fetch credentials не ограничены destination; подтверждено, внешняя утечка не проверена. | Нужен scoped API transport, а не глобальная подмена fetch. | G03; отдельный legacy fix при его разрешении, не скрытая правка G01. |
| RD05 | Tests signer/validator разделяют способ построения строки подписи; подтверждено. | Положительные тесты могут повторять одну ошибку. Совместимость текущей строки с Telegram здесь не установлена. | G03 независимые проверенные векторы; не объявлять текущую auth готовой к переносу. |
| RD06 | Demo общий кошелёк, числовые поля integer/number и кодовый каталог; подтверждено. | Целевые личные ledger/refs не получаются переименованием одного поля. | G04/G07/G08; импорт распределения по O10. |
| RD07 | Старый purchases не фиксирует исходную цену/исполнение; подтверждено схемой. | Нельзя восстановить обязательства по текущей цене награды автоматически. | G09/G13, quarantine неизвестного и явные решения. |
| RD08 | Целевые CAL/COR/BEN/LIF/уголки не представлены полными контрактами в просмотренных legacy/demo путях. | Некоторые существующие happy paths полезны, но не заменяют новый MVP. | G07/G09/G10/G11; полная приёмка по AC/DBT. |

Критичность относится к готовности целевого выпуска, не к утверждению об эксплуатации или потере данных в текущем приложении. Здесь не выполнены исправления, эксплуатационные пробы или новые тесты протоколов.

## 5. Открытые зависимости после аудита

G02-A может выполняться без выбранных цен, финального art, реальных import mappings и пользовательских auth/session политик: в нём нет покупок, identity или семейных данных. O01/O09 остаются входом G03; QDB01 — затронутых календарных команд; O10 — реального переноса; O12/O13 — баланса, ресурсных профилей и релиза. LimitsProfile authoring не реализуется в G02-A и остаётся обязательным перед G04.

Наличие Docker/свободного порта/образа PostgreSQL и фактический доступ к нему не проверялись командами в этом read-only этапе. G02-A должен проверить их перед созданием своей среды. Невозможность создать disposable DB блокирует соответствующую проверку; запрещён fallback на уже работающую семейную БД.

## 6. Оценка и следующий результат

| Объём | Оценка уверенности | Основание |
|---|---|---|
| Границы G02-A | Высокая по составу, средняя по трудозатратам | Нет доменной миграции/UI/реальных данных; нужно отделить импорты, конфигурацию, контракты и harness. |
| G02-B таблицы/миграции | Средняя | Принятые модели есть, но generated DDL/constraints ещё не проверены на disposable PostgreSQL. |
| G03/G07/G09 | Низкая для календарной оценки | O09/QDB01 и выявленные расхождения требуют отдельной реализации, не поверхностной адаптации старого сервиса. |
| G05/G06/G12 | Низкая для стоимости art | Демо не final; нет принятого пилота, ассортимента и измеренного времени производства. |

Календарные дни и стоимость не назначены: отсутствуют состав/доступность команды и художественная производительность. Границы первой работы конкретны в [карточке G02-A](G02_FOUNDATION_CARD.md); после неё фактический объём и время проверок уточнят следующий блок. G01 не выдаёт неподтверждённый процент «готовности приложения».
