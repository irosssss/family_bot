## 1. Независимая оценка и доказательства

Обновление 2026-09-07: обнаруженный ниже legacy-дефект затем [исправлен отдельным разрешённым этапом](TELEGRAM_AUTH_FIX.md). Таблица сохраняет результаты исходного аудита до исправления; синтетический probe относится к прежней версии.

| Утверждение | Статус | Основание / следствие |
|---|---|---|
| Telegram identity и семейные полномочия различаются. | Принято A01–A16; проектное решение | Telegram ID связывается с Account, а семейные права — с конкретной действующей привязкой. |
| Старый validator подписывает URL-кодированные пары; тестовый signer использует тот же подход. | Проверенный локальный факт | [telegramAuth.ts](../../src/utils/telegramAuth.ts:22), [тестовый helper](../../tests/telegramAuth.test.ts:16). Старые зелёные тесты не доказывают совместимость. |
| Канонизация старого validator расходится с проверенной сторонней реализацией. | Подтверждено синтетическим примером | [Результат](../../work/g03-a/canonicalization-probe.json): корректно подписанные разобранные значения отклонены; подпись закодированных пар принята. Настоящие initData/секреты не использовались. Это доказательство конкретного расхождения, не end-to-end проверка живого бота. |
| Проверка возраста initData не делает его одноразовым. | Вывод из модели bearer-данных | Старый лимит 24 часа ограничивает возраст, но не количество обменов. Нужны отдельные сессии и контроль повторного обмена. |
| PIN из шести цифр имеет небольшой перебираемый набор. | Свойство принятого формата | PIN не служит самостоятельным интернет-входом. Нужны проверенная identity, серверное ограничение попыток, защищённый verifier и восстановление. |
| Продукт работает на localhost:3000; 3101 был служебной пробой G02. | Уточнение пользователя | Блокировку 3101 нельзя объявлять недоступностью интерфейса игры. В этом этапе серверы/браузер не запускались. |

Telegram описывает HMAC-SHA-256 с ключом, полученным из bot token и WebAppData, и отдельную Ed25519-проверку для третьих сторон. Проверка auth_date дополняет подпись. Для HMAC проект исключает hash; для Ed25519 правила исключают hash и signature и добавляют bot_id. Режимы нельзя смешивать или использовать как неявный fallback. [Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

Разбор query перед канонизацией независимо сверён с [исходником init-data-golang](https://github.com/Telegram-Mini-Apps/init-data-golang/blob/master/validate.go) и [его signer](https://github.com/Telegram-Mini-Apps/init-data-golang/blob/master/sign.go). Это исходники авторов сторонней библиотеки, не заявление об официальном статусе библиотеки Telegram. Внутренние тесты G03-B должны закрепить проверенный вариант байтов; ссылку на изменяемую ветку нужно зафиксировать ревизией при заимствовании кода. Заимствования/установки пакетов в G03-A нет.

## 2. Границы доверия и угрозы

| Граница / угроза | Защита проекта | Остаток |
|---|---|---|
| Клиент подставляет actorId, profileId, familyId, role | Actor только из серверной сессии; family/profile в запросе — проверяемая цель, не доказательство полномочий. | Каждый новый handler проходит матрицу доступа. |
| Действительный вход ребёнка пытается читать покупки другого | Семейная область + владелец + режим проверяются до query/projection. Общий дом возвращает минимальный состав. | FK не решает чтение; нужен query/service guard. |
| Данные Telegram подменены/переупорядочены/декодированы дважды | Единый строгий parser, одна канонизация, проверка подписи до использования identity. | Внешний подписанный формат допускает новые поля, закрытый внутренний DTO — нет. |
| Украден свежий initData / гонка обмена | Короткое окно, одноразовый обмен по каноническому отпечатку, атомарная фиксация. | Кто первым предъявил украденный bearer, может выиграть гонку; TLS/отсутствие утечек обязательны. Не обещать криптографическую привязку initData к нашему challenge. |
| Ребёнок на общем устройстве открывает старую вкладку | Смена контекста инвалидирует прежний bearer; новый запуск не восстанавливает adult grant. | Сервер не может достоверно определить закрытие окна по клиентскому событию; есть серверные TTL/idle. |
| Перебор PIN / атака блокировками | Короткий PIN доступен только после verified identity; лимиты по защите взрослого, запуску и сетевому источнику; атомарные счётчики. | IP не является личностью; общая сеть не должна навсегда блокировать семью. |
| Украден dump БД | PIN KDF + отдельный pepper; высокоэнтропийные токены хранятся как verifier. | Компрометация сервера вместе с pepper не устраняется одной схемой хранения. |
| Подмена кандидата при приглашении/recovery | Неизменный candidate_account_id, operation ID, expected revisions; повторная проверка одобряющего. | Имя/аватар Telegram не доказывают личность знакомого. Взрослый сверяет человека вне приложения. |
| XSS / утечка через логи и URL | CSP, экранирование UGC, минимум внешнего JS; секреты не логируются и не передаются в аналитику. | In-memory bearer доступен исполняющемуся XSS; это отдельная обязательная проверка. |

Не используются имя профиля, username, номер телефона из произвольного JSON, скриншот или знание баланса как доказательство права. До выбора O01 не обещается собственный Telegram-вход для любого возраста/страны.

## 3. Объекты и область действия

| Объект | Область | Роль в протоколе |
|---|---|---|
| Account / ExternalIdentity | Глобальная identity | Уникальная проверенная пара provider/subject; Telegram ID хранится канонической строкой. Создание Account не создаёт Family/Player. |
| MemberProfile | Одна семья | Родитель/ребёнок, статус участия. Имеющийся профиль остаётся при смене входа. |
| AccessBinding | Семья + профиль + Account | adult_membership / own_child / managed_child. У managed manager той же семьи и Account, указывает действующего взрослого. |
| SessionContext | Семья + binding + профиль + режим | Непрозрачный bearer, expiry, revocation; серверные ссылки и ревизии. |
| AdultAccessProtection | Взрослый в одной семье | Личный PIN, credential revision, ссылка на политику. |
| RecoveryCredential / RecoveryRequest | Тот же взрослый в той же семье | Секрет восстановления или одобрение другого взрослого; authorized ещё не обычный доступ. |
| IdentityExchange / AccessLaunch | До семьи; предлагаемое техническое дополнение | Receipt обмена и короткий проверенный контекст запуска. Не создавать фиктивную семью для до-семейного входа. |
| SecurityAttemptWindow | Защита/запуск/сеть; предлагаемое дополнение | Серверный лимитер и expires_at. Не клиентский localStorage и не игровой журнал эффектов. |

Новые технические дополнения уточняют ранее предусмотренный access receipt до семьи. Они требуют отдельной схемы/индексов и политики хранения при реализации; в G02 таблицы не добавлялись.

## 4. Проверка Telegram и начальный обмен

1. Наш frontend отправляет исходную строку initData в body единственного identity-exchange endpoint. Не размещает её в URL и не прикладывает ко всем игровым запросам. initDataUnsafe не является доказательством.
2. До криптографии применяются лимиты байтов/числа полей. Query разбирается ровно один раз: проверяются некорректные percent-escape/UTF-8, пустые и дублирующиеся ключи, включая дубли после декодирования. Нельзя молча брать первое/последнее значение. Запрещены реальные CR/LF в именах/значениях, создающие неоднозначную строку подписи.
3. Для HMAC в проверку входят все разобранные поля, кроме hash, включая signature, если она присутствует. Значения JSON остаются исходными декодированными строками: не parse/stringify перед проверкой. Сортировка ключей ASCII, разделитель LF. Новое внешнее поле включается в подпись, но не получает полномочий и не попадает автоматически в наш DTO.
4. В режиме HMAC сервер использует только токен ожидаемого бота из защищённого runtime; отсутствие ключа — отказ. Сравниваются буферы SHA-256 одинаковой длины timing-safe способом. Строгий формат hash обязателен. Ed25519 не включается в MVP как запасной путь при ошибке HMAC; его можно добавить отдельным контрактом.
5. auth_date — целые секунды; время берётся с сервера. После подписи проверяются окно свежести и небольшое допустимое опережение. user — JSON-объект с допустимым целочисленным id; неверные типы, дубли JSON-ключей и небезопасные числа отклоняются. Проекция содержит provider/subject, verification method/version и verified_at; имя/фото — необязательные внешние атрибуты, не роль.
6. Отпечаток обмена строится из bot/environment и проверенного hash, а не из сырого порядка query. Вставка receipt уникальна и атомарна с выдачей AccessLaunch. Один initData не создаёт неограниченные независимые запуски. Повтор после потери ответа возвращает общий ключ повторного входа; пользователь переоткрывает Mini App для нового initData. Идемпотентный возврат секретного ответа не реализуется через обычный журнал.
7. AccessLaunch позволяет увидеть только собственные доступные способы входа/настройки и завершить приглашение/recovery. Семейные данные выдаются после разрешённого выбора binding. При отсутствующей identity показывается onboarding, а не чужая семья или demo-режим.

Для проверки криптопримитива используются независимые [векторы RFC 4231](https://www.rfc-editor.org/info/rfc4231/); они не проверяют Telegram-канонизацию. Для неё нужны отдельные сохранённые синтетические golden cases, независимо рассчитанные другим инструментом, включая Unicode, %, +, &, JSON escaping и signature. Настоящий запуск тестового бота — последующий отдельно разрешаемый integration gate, не выполнен в G03-A.

## 5. Два способа детского доступа

| Сценарий | Разрешённая последовательность | Что сохраняется |
|---|---|---|
| Собственный Telegram ребёнка | Проверить identity → выбрать действующий own_child → проверить активные семью/профиль → выдать own_child session. | Тот же profile_id/player; никаких starter gifts при входе. |
| Через устройство взрослого | Проверить identity взрослого → настроенная защита → его PIN → выбрать своего ребёнка → проверить managed binding → атомарно погасить взрослый bearer и выдать managed_child session. | Один профиль ребёнка, независимо от числа управляющих взрослых. |
| Сменить ребёнка / вернуться к управлению | Managed session сама не авторизует действие. Новый PIN соответствующего взрослого + актуальная identity/привязка → новый контекст; старый bearer больше не принимает команды. | Покупки/прогресс обоих детей не меняются. |
| Повторно открыть Mini App | Секреты сессии не восстанавливаются из localStorage; новый запуск и повторный PIN перед взрослым режимом. | Собственный вход ребёнка не требует родительского PIN. |
| Несколько вкладок | Каждая команда привязана к контексту, выдавшему bearer; старый контекст после переключения не может выполнить отложенную команду. | Просмотр аватара не переключает actor. |

На этапе проектирования выбран **непрозрачный bearer только в памяти вкладки**, передача через Authorization нашему точному API origin. Это позволяет не делать сторонние cookies обязательной зависимостью Mini App. Токен не хранится в localStorage/sessionStorage/URL/Telegram CloudStorage и не используется как публичный ID. Внутренние идентификаторы контекста не секреты и сами по себе доступа не дают.

Production — HTTPS; API и frontend предпочтительно одного origin. Клиент отвергает внешние origin до добавления Authorization; redirect на другой origin не переносит credential. CORS — конкретный allowlist, не wildcard. Мутации требуют JSON/Authorization; GET не изменяет состояние. Если позднее вводится cookie-аутентификация, нужен отдельный согласованный CSRF-контракт, а не механическая смена способа хранения токена. [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

parent_session_id остаётся источником отзыва managed session. Истечение краткого adult grant не должно само по себе разлогинивать ребёнка. Поэтому предлагаются раздельные expires_at общего семейного контекста и adult_grant_expires_at/idle_expires_at взрослого полномочия. При переходе в детский режим старый bearer погашается, но запись происхождения остаётся до своего expires_at; это не revoked_at. Для этого состояние verifier токена отделяется от отзыва SessionContext: погашенный verifier больше не аутентифицирует запросы и не восстанавливается при новом PIN. Явный отзыв, отзыв binding или protection revision запрещает и производные детские сессии. Эти поля/семантика — уточнение SessionContext на приёмку, а не уже реализованная схема.

## 6. Матрица полномочий

| Действие | Только verified identity | Adult + действующий grant | Own_child | Managed_child |
|---|---|---|---|---|
| Общий дом/видимые герои/общая цель | Нет | Своя семья | Своя семья, минимальная проекция | Своя семья, минимальная проекция |
| Дела, история, баланс и покупки ребёнка | Нет | Управляемая семья | Только свой профиль | Только выбранный профиль |
| Покупка личного предмета / выбор питомца | Нет | Не действие родителя от имени ребёнка | Свой профиль | Выбранный профиль |
| Настройка дел и реальных наград, проверка выполнения | Нет | Да, в семье | Нет | Нет |
| Смена профиля на общем устройстве | Нет | После подтверждения PIN | Нет | Требует PIN взрослого |
| Приглашение, перепривязка, recovery, архив, отзыв чужих сеансов | Нет | Свежее подтверждение PIN и условия A02/A10–A16 | Нет | Нет |
| Onboarding / принять приглашение как кандидат | Ограниченный challenge | По назначению | Только собственное подтверждение кандидата | Не выдаёт identity ребёнка |
| Создание контентного пакета | Нет | Семейная роль не разрешает | Нет | Нет |

Каждая мутация сначала аутентифицирует session, затем в транзакции блокирует строку family и заново проверяет membership/binding/protection/context revisions, target и operation ID. Отзыв использует ту же семейную блокировку: операция либо законно закоммичена до отзыва, либо отклонена после него. Ранее закоммиченные игровые результаты не отменяются отзывом доступа.

Чтение использует согласованную проверку session и области; после зафиксированного отзыва новое чтение запрещено. Ответ, уже выданный до отзыва, нельзя отозвать из памяти получателя. Для будущих WebSocket/SSE нужны проверка контекста на каждом защищённом сообщении и отключение после отзыва, а не одна проверка при connect.

## 7. Приглашения и первичная настройка

| Переход | Предусловия и атомарность |
|---|---|
| Создать первую семью | Verified Account + явное действие взрослого; условия O01/согласий до живого запуска. Семья и первый parent profile создаются одной операцией. До настройки PIN и подтверждения сохранения recovery-кода взрослое управление и managed access закрыты. |
| issued | Взрослый со свежим PIN выбирает назначение. Child_link указывает существующий child profile; adult_join не резервирует скрытую роль владельца. Случайный invite secret отдаётся только инициатору; автоматическая отправка ботом не подразумевается. |
| issued → claimed | Кандидат доказывает Telegram identity и намерение; candidate фиксируется CAS и не подменяется. Повтор того же кандидата идемпотентен; другой получает отказ. До одобрения — только статус запроса. |
| claimed → approved → consumed | Взрослый видит именно проверенного кандидата и подтверждает свежим PIN. Срок/роль/профиль/состав полномочий повторно проверяются. Approved не даёт чтения; потребление и создание binding атомарны. |
| adult_join consumed | Новый parent profile/участие создаётся единожды, membership_revision меняется. Новый взрослый проходит собственную настройку защиты до управления. |
| child_link consumed | Existing child profile получает один own_child binding; вторую активную связь не создать. Замена требует отдельной команды с явным отзывом старой. |
| revoked / expired | Финальные состояния без новых прав. Истечение определяется сервером при запросе, а не только cleanup cron. Выход issuer инвалидирует его незавершённые приглашения. |

Секрет приглашения не является достаточным правом вступления: обязательны identity кандидата и одобрение взрослого. Текст/изображение имени — помощь взрослому для сверки, но не подтверждение знакомства. Ссылка формируется из настроенного origin/бота, не из произвольного Host; параметры ссылок очищаются из аналитики и referrer.

## 8. PIN, восстановление и отзыв

PIN: ровно шесть ASCII-цифр, включая начальные нули, передаётся как строка. На сервере предлагается Argon2id с индивидуальным salt и отдельным pepper из защищённого runtime; параметры/версия сохраняются с verifier. Минимум-кандидат m=19456 KiB, t=2, p=1 соответствует рекомендации [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); нагрузочное измерение и выбранный пакет обязательны до реализации. Ограниченная энтропия PIN сохраняется даже при хорошем KDF. При утрате pepper нет тихого fallback; используется проверенный recovery.

Recovery-код: предлагается 160 случайных бит с удобной группировкой Base32 и контрольным символом; последний не добавляет энтропию. Секрет показывается один раз в настройке и не отправляется в тот же Telegram. В хранилище verifier + public locator/версия, отдельно от игровых проекций. «Сохранён вне устройства» — подтверждение взрослого, а не доказуемое сервером действие.

| Сценарий | Протокол |
|---|---|
| Забыт PIN | Verified Account → запрос конкретного взрослого/семьи → recovery-код либо подтверждение другого действующего взрослого со свежим PIN → короткое право только на завершение восстановления. |
| Потерян Telegram | Новый verified Account → конкретный recovery request → прежний семейный recovery-код либо второй взрослый подтверждает именно нового кандидата. Не перепривязывать ExternalIdentity глобально вместе со всеми семьями. |
| Завершить recovery | Кандидат дважды вводит новый PIN; family lock + expected protection revision + неизменный candidate + проверенное основание. Одной транзакцией меняются семейная привязка/защита, расходуется старый код и отзываются старые семейные сеансы, включая производные. |
| Выдать новый код | После commit — ограниченная настройка новой защиты и показ нового recovery-кода с подтверждением сохранения. Потерян ответ — старый код не оживает; повторное получение идёт через короткий setup-контекст, с ротацией ещё не подтверждённого нового кода. Полноценный adult access до завершения настройки закрыт. Затем обычный вход, без автоматической взрослой сессии. |
| Recovery одобрил другой взрослый | На завершении снова проверяются его действующее участие, та же семья и неизменная revision одобрения/защиты. Выход/отзыв одобряющего делает запрос непригодным. |
| Нет кода и другого взрослого | Автоматический путь отсутствует по A12. Не вводить восстановление по персональным данным или скрытый admin bypass. |
| Отозвать own_child | Отзываются соответствующий binding и все его сессии; managed bindings и игровой профиль остаются. Повторный вход не восстанавливает связь автоматически. |
| Завершить чужие семейные сеансы | Свежий PIN инициатора, лимиты A15; отзываются сеансы другого взрослого и их managed descendants, членство сохраняется. |
| Выход / согласованное исключение | Условия A14/A16 и последний взрослый; членство, PIN/recovery и незавершённые процессы данного взрослого закрываются в этой семье. Независимые входы детей/других взрослых и другие семьи не меняются. |

Одноразовость, защищённое хранение, ограниченное право recovery, общие сообщения об отказе и обычный вход после сброса опираются на [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). Конкретное согласованное восстановление через второго взрослого — правило нашего продукта.

## 9. Ошибки, локализация и эксплуатация

| Ситуация | Пример ключа | Поведение |
|---|---|---|
| Неверная/устаревшая identity | access.identity_invalid / access.launch_expired | Новый запуск; без сырого initData или криптографических деталей в ответе. |
| Истёк/отозван контекст | access.session_expired / access.session_revoked | Остановить очередь команд, очистить локальный bearer, показать вход. |
| Нужен PIN / свежее подтверждение | access.adult_confirmation_required | Сохранить только несекретный черновик; не повторять мутацию автоматически. |
| Слишком много попыток | access.retry_later | Серверный retry_after; таймер UI информирует, не защищает. |
| Контекст/кандидат изменился | access.context_changed / access.request_changed | Обновить состояние и заново подтвердить намерение. |
| Недопустимая цель / чужие данные | access.not_available | Не различать «не существует» и «чужой» для неавторизованного получателя. |

Все системные тексты — ключи локализации; пользовательские имена остаются UGC. PIN-поля не записываются в telemetry/session replay и не используются в автодополнении публичных форм. Audit содержит outcome key, operation ID, внутренние ссылки, policy/revision и серверное время; без PIN, bearer, recovery, initData, полного HTTP-body или копий Telegram user JSON.

Session registry — серверный источник отзыва; MVP может использовать PostgreSQL без обязательного Redis. Лимитер должен быть атомарным между процессами и сохранять блокировку при рестарте. Расширение на отдельное хранилище допускается через интерфейс с теми же гарантиями. Доступные семейные права не кешируются без механизма согласованной инвалидации.

Стоимость поддержки: отдельные версии verifier/policy, тесты канонизации при обновлении Telegram/SDK, ротация ключей, миграции активных сессий, нагрузка KDF, кроссплатформенная проверка памяти/перезапуска и lifecycle-история. Готовый auth-provider не отменяет семейные привязки и A01–A16; смена транспорта не должна менять profile_id или игровые права. Не создаётся собственная криптография или универсальный исполняемый security-DSL.
