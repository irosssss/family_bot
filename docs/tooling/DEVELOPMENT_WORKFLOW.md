# Рабочий процесс: от задачи до доказательства

Применять соразмерно задаче. Исправление текста не требует поиска референсов;
backend-задача не требует ARTEMIS. Это правила проекта, а не список обязательных
внешних сервисов. Обоснование: [исследование 21.09.2026](RESEARCH_2026-09-21.md).

## Перед работой

Прочитать AGENT_MEMORY и актуальный контракт. Проверить working tree, определить
границы изменения и наблюдаемый результат. Отделить действующий runtime от макета,
локального demo и ещё не подключённого backend.

## Дизайн

1. Сформулировать пользователя, действие и нужные состояния экрана.
2. Использовать принятые компоненты и токены. Inspo нужен только при открытом выборе
   направления или отсутствии подходящего паттерна. Если MCP недоступен, сообщить
   это и использовать уже известные референсы/браузер; не изображать вызов сервера.
3. Для исследования задать обезличенный brief, mobile при мобильной задаче, небольшой
   limit/maxTokens. Начать с одного recommend, затем при необходимости уточнить поиск.
4. Для каждого выбранного референса записать URL, заимствуемый принцип и ограничения.
   Рекомендации маркетинговых сайтов не являются спецификацией игрового интерфейса.
5. Зафиксировать палитру, типографику, плотность, главный CTA и состояния.
   При новом направлении сравнить 2–3 варианта на одном содержимом. Утверждённый
   стиль не пересматривать без задачи на изменение направления.
6. Менять конкретные компоненты. Проверить кириллицу, длинные имена, пустое состояние,
   ошибку и ожидание. Удалить элементы без пользовательской функции.

В Family Chores RPG: V3_BASELINE имеет приоритет; 375/390px, цели касания >=44px,
без эмодзи, пользовательские персонажи и принятый арт. Мир остаётся заморожен.
Новые runtime-ассеты регистрировать в ASSET_MANIFEST; исходники генерации вне public.

## Реализация и доказательства

- Независимые чтения объединять; зависимые изменения и проверки выполнять по порядку.
- Большие логи сохранять в `work/<task>/`; в ответ давать итог, exit code, путь и
  релевантные строки. Ошибка или сокращение вывода не означает PASS.
- Выполнить `npm run lint`; подобрать тесты к изменению. Для UI — браузер 375/390px,
  реальные действия и скриншоты. Для поведения — ожидаемое состояние до/после,
  повторное действие, reload и проверка награды/прав, где это относится к задаче.
- ARTEMIS использовать после доступности тестового Android-стенда, когда проверяется
  Android/Telegram WebView. Обычный браузер не выдавать за Telegram или iOS.
- По завершении записать проверенное, непроверенное и остаточный риск. Обновлять
  AGENT_MEMORY только для подтверждённого изменения или урока.

## Карточка результата

```text
Задача / границы:
Контракт и инварианты:
Среда: commit + dirty state, browser/device, URL, synthetic fixture
Референсы и выбранные принципы (если нужны):
Изменения:
Проверка: команда/действие, ожидаемое, наблюдаемое, exit/status
Доказательства: пути логов/скриншотов, trace ID при наличии
Не проверено / ограничения:
Следующее конкретное действие:
```

Не вводить второй агентный runtime ради самого runtime. Пилот SoL-Pi оценивать
отдельно: успех задачи и доказательства обязательны; экономия без сопоставимого
качества не является улучшением процесса.
