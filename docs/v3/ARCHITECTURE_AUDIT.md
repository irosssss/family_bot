# Family Life RPG V3 — архитектурный аудит

Дата: 2026-09-09. Область: отдельная ветка `codex/family-life-v3`, третий вариант. Основа проверки — исходники, существующие контракты и два новых документа. Основной вариант и Folio не изменяются. Сервисы и реальные семейные данные при этом аудите не использовались.

## Решение для третьего варианта

Пользователь отдельно подтвердил взрослых-игроков **только для V3**. Поэтому право управлять семьёй и наличие игрового профиля здесь независимы. Это принятое изменение V3, а не изменение правил основного приложения или существующей схемы `rpg.players`.

Первый этап — независимая мобильная оболочка, синтетические примеры экранов и места будущей графики. Без начислений, сохранения данных семьи, авторизации, платежей или загрузки игровых ресурсов. Прототип показывает предполагаемый продуктовый поток; он не выдаёт локальное изменение экрана за подтверждённую сервером операцию.

Новое GDD не заменяет автоматически действующий контракт всех вариантов. Его формулы, ассортимент, игровые системы и технические таблицы требуют сверки. Уже подтверждённое решение взрослых-игроков учитывается сразу; остальные расхождения остаются явными.

## Границы кода

Точка входа: `family-life-v3.html` → `src/v3/main.tsx` → `src/v3/App.tsx`.
Стили: только `src/v3/v3.css` и локальные классы `.v3-*`.
Реестр: `src/v3/assets/registry.ts`.
Контракт: `src/v3/assets/contracts.ts`.
Рендер заглушки: `src/v3/assets/AssetSlot.tsx`.

| Слой | Этап 1 | После принятия зависимого этапа |
|---|---|---|
| UI | Навигация, вкладки, состояние открытых панелей, выбранный синтетический пример. | Отображение разрешённой серверной проекции и результатов команд. |
| View fixtures | Предопределённые взрослые и дети, дела, предметы и прогресс; без данных пользователя. | Сохраняются как тестовые fixtures, не становятся миграцией. |
| Commands | Только экранные сценарии, без реальных наград. | Явные DTO намерений: submit/approve/purchase/equip/claim; клиент не присылает новый баланс. |
| Application ports | Границы описаны в документации; ненужные серверные адаптеры не создавать заранее. | StateQuery, CommandGateway, ContentResolver, Identity/Capability adapter, Clock, ID source. |
| Domain | Нового игрового движка на этапе 1 нет. | Чистые правила и обработчики команд отдельными модулями; один владелец каждого состояния. |
| Persistence | Нет localStorage/sessionStorage/IndexedDB для семейного состояния. | Транзакционный серверный адаптер с scoped receipts и отдельными таблицами/версиями по принятому проекту. |
| Art | `AssetSlot` всегда `not_supplied`. | Resolver точных ревизий и отдельный renderer после принятия профиля и пакета. |

Допустимое переиспользование — чистые низкоуровневые примитивы с проверенной границей зависимостей: например правила `ContentRef`, `AssetRef`, exact revisions, закрытая валидация и семантика идемпотентности. На этапе 1 даже эти server-модули не нужны в browser bundle. Не следует создавать «новый движок» копированием всей `src/demo` с переименованием типов.

В дальнейшем независимость V3 означает самостоятельный продуктовый адаптер и экранные проекции, а не вечное дублирование доступа, ledger, операций и контентного compiler. Общее ядро выделяется только после проверки одинаковых инвариантов. Отличающееся правило взрослых-игроков должно иметь явную версию/capability, а не обход child-only check.

## Следующие сущности и операции

| Контур | Минимальные сущности | Что должно оставаться отдельным |
|---|---|---|
| Доступ | Account, Family, MemberProfile, AccessBinding, CapabilitySet, PlayerProfile. | Кто действует, кем управляет и чей игровой прогресс меняет; просмотр героя не смена авторизованного actor. |
| Дела | TaskDefinitionRevision, TaskOccurrence, ParticipantAllocation, CompletionAttempt, CompletionSettlement. | Условия задания, конкретный календарный экземпляр, попытка проверки и однократный расчёт. |
| Экономика | CurrencyDefinition, Wallet, WalletEntry, Reservation, RewardPolicyRevision, RewardBudgetBucket. | Расходуемые валюты; Hero XP, Family XP, сезонный XP и заряд Ultimate являются отдельными видами прогресса. |
| Прогресс | ProgressGrant, HeroProgress, FamilyProgress, WeeklyGoal, GoalContribution, MilestoneClaim. | Настроенная цель и уже принятый вклад; изменение правила не переписывает историю. |
| Каталог/магазин | ContentDefinition/Revision, AssetRevision, VisualBinding, VisualProfileRevision, Offer/OfferRevision, Purchase. | Цена и окно продажи не свойства файла. Покупка фиксирует условия и получателя. |
| Владение | OwnedEntitlement, AppearanceSelection, OwnedPet, EggAcquisition, PetProgress, ActiveCompanion, HouseConfiguration, TrophyGrant. | Получение, примерка, надевание, просмотр питомца и выбор спутника — разные операции. |
| Сезоны/бой | SeasonDefinitionRevision, SeasonRun, FamilyEnrollment, ParticipationSnapshot, EventMemberState, EventFamilyState, EncounterRun, DamageContribution, RewardClaim. | Определение сезона и семейный запуск; текущий состав семьи и зафиксированные условия начавшегося боя. |
| Поздняя коммерция | FamilyEntitlement, PurchaseIntent, ProviderReceipt, SubscriptionPeriod, Refund/Reconciliation. | Игровой Gold, игровые Crystals и внешняя оплата; неподтверждённый платёж не выдаёт право. |

Это список необходимых границ, не поручение создать все таблицы в первом этапе. Family Pool/Stars, выдача взрослому за собственное дело, review его задач и правила общих покупок требуют отдельных контрактов, даже после принятия взрослых-игроков.

Будущий ledger хранит минимум: `entry_id`, `family_id`, типизированного владельца кошелька (`player` либо `family`), `currency_ref`, подписанную целочисленную `delta`, `entry_kind`, `operation_id`, `cause/source/effect_key`, actor, beneficiary, `policy_revision`, момент принятия, при необходимости календарный/сезонный snapshot, ссылку на исходное начисление для компенсации. На JSON-границе денежные игровые количества передаются в точном целочисленном формате; float не используется для остатка и списания.

Доступный баланс — проверяемая проекция ledger и активных резервов. Резерв не является списанием. Исправление добавляет связанное компенсирующее событие, а не стирает первоначальную историю. Бизнес-уникальность settlement/claim действует независимо от срока хранения HTTP receipt.

События: `CompletionSubmitted`, `CompletionAccepted`, `CompletionReturned`, `RewardSettled`, `PurchaseCommitted`, `AppearanceSelected`, `PetAcquired`, `EncounterProgressed`, `EncounterDefeated`, `SeasonRewardClaimed`. Их envelope содержит event ID/schema version, family scope, aggregate ID/revision, server time, actor, correlation/causation и закрытый payload. Лента — локализованная проекция событий, не единственный журнал экономики и не исполняемые строки текста.

Для начисления нужен один атомарный результат: проверка полномочий и неизменных условий → settlement → ledger/progress/entitlement → receipt. Для внешней доставки событий позже пригоден transactional outbox с повторяемым обработчиком. Полное event sourcing всей БД для этого не требуется.

## Что завершает этап 1

1. Независимый entry открывает V3 без основной демо, target server, Telegram SDK и фоновых интеграций.
2. Дом, дела, герой/коллекция, приключение и семейная область показывают синтетические состояния. Взрослые имеют игровое представление независимо от административных действий.
3. Все 13 мест графики берутся из реестра. На экранах отсутствуют игровые bitmap, SVG-иллюстрации, canvas и замаскированные CSS-спрайты.
4. Для каждого места опубликованы назначение, планируемый путь, пропорция, кандидат canvas, anchor, слои, варианты, места использования и будущая проверка.
5. Зафиксированы браузерные доказательства на 375/390 px и широкий/большой состав. Серверные сценарии и арт этим не объявляются принятыми.

Не входят: production auth, начисление XP/Gold, настоящий ledger, миграции, покупки/возвраты, случайные выдачи, бой и сезонные timers, платежи, загрузка/генерация/подмена графики, подключение бота или публикация.
