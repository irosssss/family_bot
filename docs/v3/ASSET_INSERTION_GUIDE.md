# Family Life RPG V3 — куда добавлять будущие ассеты

Версия 1, 2026-09-09. Сейчас **не добавлено ни одного игрового изображения**. Все 13 мест имеют статус `planned`; `AssetSlot` не содержит загрузчика. Этот документ — техническая карта будущей вставки, а не утверждённая артдирекция.

Источник UI-мест: [`src/v3/assets/registry.ts`](../../src/v3/assets/registry.ts). Контракт: [`contracts.ts`](../../src/v3/assets/contracts.ts). Компонент: [`AssetSlot.tsx`](../../src/v3/assets/AssetSlot.tsx). Изменение `targetPath` в реестре **не подключает файл** — компонент это поле вообще не читает.

## Три разные идентичности

| Что | Пример | Что меняется независимо |
|---|---|---|
| Место в UI (`slotId`) | `hero.adult` | Данные выбранного взрослого, его одежда, файл изображения. |
| Предмет/определение (`ContentRef`) | `life:equipment/explorer_shirt`, revision 1 | Имя/перевод, предложение магазина, способ получения, visual bindings. |
| Бинарный ресурс (`AssetRef`) | `life:asset/explorer_shirt_adult_torso`, revision 1 | Размещение файла внутри immutable release и его проверяемые bytes. |

Член семьи, владелец вещи, экземпляр питомца и его пользовательское имя не входят в системный `slotId` или имя PNG. Один слот героя повторяется для разных членов семьи. У конкретного экземпляра React key/DOM identity задаётся вызывающим UI отдельно.

Не следует сохранять путь PNG в кошельке, покупке или игровом профиле. Покупка фиксирует предмет/право и условия; внешний вид ссылается на совместимые определения; resolver находит точные visual bindings и файлы.

## Контракт места

| Поле | Требование |
|---|---|
| `id` | Стабильное `category.name`, без семейных ID и номера ревизии. Не переиспользовать для другой роли. |
| `label`, `description` | Понятное назначение. UI может переопределить подпись для контекста; пользовательский текст не исполняется как HTML. |
| `category` | Закрытый тип: scene/hero/boss/pet/item/home/collection. |
| `aspectRatio` | Пропорция **места в интерфейсе**. Резервируется до появления графики и при ошибке. |
| `logicalCanvas` | Положительные width/height кандидата исходника. `geometryStatus:'candidate'` явно запрещает считать его утверждённым экспортным стандартом. |
| `targetPath` | Шаблон будущего runtime-файла, только для инструкции. Ни `src`, ни URL, ни разрешение скачать ресурс. |
| `anchor` | Именованная точка в нормализованном прямоугольнике, `space:'normalized'`, x/y в [0,1]. Это координаты каркаса UI, не готовый rig. |
| `layers` | Семантические роли предполагаемых частей. Порядок/occlusion каждого финального профиля проверяются отдельно. |
| `states` | Планируемые **статичные** visual variants. Наличие строки не означает необходимость отдельного файла, анимации или игровой механики. |
| `screens` | Все места использования общей сборки. Исправление должно проверяться во всех перечисленных контекстах. |
| `status` | Сейчас только `planned`. Переход к готовому ресурсу требует будущего resolver/renderer и принятого контентного контракта. |

Пример использования уже работающего компонента:

```tsx
<AssetSlot slotId="hero.adult" label="Герой Алексея" />
<AssetSlot slotId="home.room" inspect onInspect={openAssetDetails} />
```

API намеренно не принимает `src`, bitmap, renderer callback, произвольный HTML, SVG или canvas. Обычное место содержит только рамку и текст; отдельная кнопка «Параметры» появляется при `inspect` и `onInspect`. Неизвестный ID показывает «Место не зарегистрировано», а не подставляет первый ассет каталога.

## Что подготовить для каждого места

### `home.room`

- `shell`: стены, пол и неотделимая архитектура; файл может быть непрозрачным.
- `rear_furniture`: задние предметы только если они действительно меняются независимо.
- `middle_props`: сменяемые элементы между группами участников.
- `foreground`: только обоснованные перекрывающие части, не закрывающие лица и управление.
- `base`, `upgraded`, `seasonal` — предполагаемые состояния. Сезон предпочтительно добавляет совместимый overlay, а не требует заново рисовать всех героев и всю мебель.

Не рисовать внутрь фонового PNG взрослых, детей, их питомцев, имена, показатели, кнопки, трофейные подписи. Будущий `SceneLayout` отдельно задаёт member slots, bounds пары герой+питомец, floor/seat/companion anchors, depth groups и размещение DOM-подписей. Число мест кадра не ограничивает размер семьи; нужен доступный список/группы.

### `hero.adult` и `hero.child`

Обе сборки используют единую систему координат **внутри принятого профиля**. Взрослые и детские пропорции проверяются отдельно. Текущее совпадение кандидатов 64×80 не означает одинаковый силуэт или универсальность вещей.

| Роль слоя | Что в нём | Когда нужен отдельный файл |
|---|---|---|
| `contact_shadow` | Контактная тень. | Если она не включена в другую согласованную часть. Не рисовать вторую тень. |
| `aura_back` | Задняя часть эффекта. | Только после решения об ассортименте; сейчас не обязательна. |
| `hair_back` | Волосы за телом/одеждой. | Для причёсок, которым это требуется. |
| `outfit_back` | Плащ/задняя часть костюма. | Если имеет отдельное перекрытие. |
| `body_underlayer` | Непрозрачная база с бесплатной нижней одеждой. | Обязательна работоспособная база после снятия вещей. Голова может входить в неё согласно профилю. |
| `legs` | Носимый низ. | При независимой смене; полный костюм может закрывать этот слот. |
| `feet` | Обувь. | При независимой смене; пара обычно одна единица владения. |
| `torso` | Верх/рукава/броня по профилю. | Когда поддерживается независимый предмет. |
| `held_back` | Часть предмета за рукой/телом. | По форме и grip конкретной позы. |
| `face` | Лицо: глаза, брови, нос, рот. | Отдельные eyes/brows только после решения об их независимой настройке. |
| `hair_main` | Основные волосы. | Стиль/цвет — варианты контента, не имена пользователей. |
| `headwear` | Шляпа/шлем. | Согласовать hidden hair layers и доступность лица. |
| `hair_front` | Передние пряди. | Только если одного hair_main недостаточно для перекрытия. |
| `hands_held_front` | Кисти/передняя часть предмета по профилю. | Не дублировать кисти уже нарисованного body; разделить на несколько bindings при доказанной необходимости. |
| `accessory_front` | Передний аксессуар. | По принятому слоту и compatibility matrix. |
| `aura_front` | Передняя часть эффекта. | Опционально; не закрывает лицо/подписи/controls. |

Порядок строк — схема для обсуждения, **не универсальный алгоритм z-index**. Финальный профиль должен задать `body_family`, `pose`, `view`, `palette_variant`, canvas, safe bounds, anchors, layer order, occupied slots, hidden layers, grip и occlusion. Одна шляпа или оружие вправе иметь несколько bindings, сохраняя одно ownership key.

Статичные варианты `neutral` и `celebration` пока только кандидаты. Не производить второй полный комплект всех слоёв ради слова celebration, пока не приняты поза и стоимость совместимости. Сидячего героя нельзя получить CSS-сжатием стоящего; до использования сиденья необходимы соответствующие body/clothing/hand variants.

### `hero.portrait`

Производный crop той же resolved appearance, что отображается в доме. Цвет кожи, волосы и одежда должны совпадать. Кандидат 64×64 задаёт место портрета, но не разрешает отрезать голову или подменять купленный образ другой иллюстрацией. Рамка, статус и selected/focus — DOM/UI. Не сохранять отдельные PNG с именами/ID реальных членов семьи в общем каталоге.

### `boss.main`

Сначала достаточно цельного статичного `boss` и, если нужен, `contact_shadow`. `phase_one`, `phase_two`, `phase_three`, `defeated` — будущие статичные варианты с одинаковой опорой и предсказуемыми bounds. Необходимость всех четырёх решается после боевого контракта; spritesheet и атака не обязательны.

HP, выбранная фаза, награда и её однократная выдача не находятся в изображении. Файл победы не должен срабатывать как команда выдачи. Не изображать потерю предметов/страдание ребёнка как наказание за пропуск дела.

### `adventure.map`

`map_background` и при необходимости `landmarks` показывают географию. Пути, узлы, кнопки и подписи привязываются к отдельным данным. Нужен обычный доступный список локаций. Перекрашенная карта не добавляет автоматически боевую механику, состояние сезона или разрешение новых мест.

### `pet.egg`

`egg` и при необходимости тень. `unhatched`/`ready_to_hatch` могут использовать один файл с разным текстом UI. Прогресс до вылупления и известность/случайность результата задаются отдельным продуктовым правилом. Не выводить `OwnedPet` из имени картинки и не выбирать первый pet каталога при ошибке.

### `pet.companion`

Цельный `pet_body`, отдельная тень при необходимости. `cosmetic_back/front` — только после принятия совместимых аксессуаров; их occlusion определяется профилем, а не текущим порядком названий в справочнике. `pet` и `companion` обозначают потенциальные стадии, не два независимых автоматически выданных питомца.

Один экземпляр имеет свой прогресс, имя и выбранную косметику. Просмотр другого питомца не меняет активного спутника. При смене видимой стадии сохранить source/content refs, не уничтожать историю получения. Для большого питомца нужен новый проверенный профиль размещения, а не увеличение поверх соседнего героя.

### `pet.corner`

Добавлено на этапе 2 для состояния выросшего питомца. В реестре теперь 14 мест. Это описание будущей графики, файл ещё не создан.

- `corner_shell`: нейтральный фон и пол уголка; допускается непрозрачный слой.
- `resting_place`: отдельное место отдыха, если оно будет меняться независимо; прозрачность вне объекта.
- `foreground`: только необходимое переднее перекрытие, не закрывающее морду питомца и кнопки.
- Кандидат холста 320×240 и отношение 4:3; произвольную квадратную иконку мебели не растягивать на весь уголок.
- Сам `pet.companion` не запекать в основу. Его локальная точка контакта сопоставляется с отдельной companion anchor раскладки уголка; конечные координаты проверяются с принятым профилем после арт-поручения.
- Никаких встроенных имён, кнопок, шкал или цены. Уголок появляется вместе с питомцем бесплатно; отсутствие PNG не закрывает доступ к нему.
- Будущая вставка: подготовить три семантических слоя или обоснованное объединение → проверить alpha/поля → зарегистрировать ревизии → связать corner definition с видом питомца → renderer в представлении `PetPreview` → проверить взрослого/ребёнка и missing resource на 375/390 px.

### `item.outfit`

По пути реестра добавляется **только превью**. Чтобы одежда действительно надевалась, нужны отдельные носимые bindings, например:

```text
public/assets/game/family_life_v3/<release>/
  item_outfit__explorer_shirt__preview__r<revision>.png
  equipment_explorer_shirt__<body_family>__<pose>__torso__r<revision>.png
```

Предмет связывает эти файлы через ContentRevision/VisualBinding. Указать поддерживаемые взрослые/детские body profiles, occupied slots и конфликты с полным костюмом. Проверить одинаковые форму/цвет превью и носимой вещи. Не переносить боевые статы вместе с картинкой.

### `item.weapon`

Превью отдельно от `held_back`/`held_front` для конкретной позы. Пример будущих файлов:

```text
public/assets/game/family_life_v3/<release>/
  item_weapon__forest_blade__preview__r<revision>.png
  equipment_forest_blade__<body_family>__<pose>__held_back__r<revision>.png
  equipment_forest_blade__<body_family>__<pose>__held_front__r<revision>.png
```

Ключевые проверки: hand_grip, кисть, локоть, направление, safe bounds. Задний/передний файл нужен только при реальном перекрытии. Два слоя не становятся двумя покупками. Нельзя получать левую руку простым зеркалированием асимметричного/подписанного арта без проверки.

### `home.furniture`

`binding` в имени означает `preview`, `back` или `front` по реальной необходимости. Файлы относятся к одному предмету. Его scene bindings совместимы с профилем комнаты; координаты floor/seat сохраняются. Передний край стола или кресла не закрывает лица и доступные действия. Для сиденья требуются seat_contact и совместимые сидячие герои.

### `family.trophy`

Статичный объект с shelf_contact. Название достижения, дата и семья — текст UI. Трофейное право выдаётся отдельной идемпотентной операцией; его наличие не определяется переключением изображения. Один общий файл используется для всех заслуживших его семей.

### `collection.cover`

Тематическая композиция 3:2 без названия, цены, процента, счётчиков и призывов к покупке внутри PNG. Название и состав — данные каталога. Обложка не доказывает владение всеми изображёнными предметами; подписать доступность и принадлежность коллекции отдельно.

## Состояния загрузки, fallback и доступность

Сейчас все места находятся только в `not_supplied`; нет запросов даже к запланированному локальному пути. Повторно загрузить нечего, поэтому не показывается неработающая кнопка retry.

| Будущее resource state | Поведение после появления настоящего renderer |
|---|---|
| `not_supplied` | Нейтральное подписанное место; ничего не загружать. |
| `loading` | Сохранить aspect/bounds, текст и доступные действия; декоративный индикатор не меняет ширину/высоту. |
| `ready` | Показывать только проверенный exact binding поддерживаемого профиля. |
| `missing` / `failed` | Сохранить выбранный предмет/питомца/профиль; нейтральная заглушка и явный повтор при существующем загрузчике. |
| `unsupported` | Понятное сообщение о неподдерживаемом профиле/версии; не подставлять похожий старый demo asset. |

UI state `selected/focus/disabled/busy` не входит в игровой bitmap. Focus — видимый CSS-контур; control — native button ≥44×44 CSS px с доступным именем. Один tap по отдельной кнопке выполняет одно действие. Маленький рисунок не является единственной hit area.

У информативной сборки доступное описание целого героя/вещи. Отдельные внутренние слои декоративные (`alt=""`/aria-hidden в будущей реализации), чтобы reader не перечислял 16 файлов. Подписи, цены, HP и прогресс остаются DOM-текстом. Не помещать интерактивную кнопку внутрь `role="img"`, который скрывает дочернюю семантику. У текущего компонента семантический `figure` и отдельная именованная кнопка inspector.

   ```text

   art-source/family_life_v3/<asset_slug>/references/
   art-source/family_life_v3/<asset_slug>/exports/
   art-source/family_life_v3/<asset_slug>/review/
   ```

4. Подготовить экспорт **кандидата** с origin/license, source digest, media type, bytes, width/height, alpha, профиль/revision, variant tuple, anchors, bounds и review evidence. Все слои одной сборки возвращаются в общий canvas. Trim требует сохранённого offset; произвольная обрезка прозрачных полей запрещена.
5. Добавить отдельные authoring-схемы и валидатор игровых ресурсов. Нынешний target compiler принимает только plain-text localization; его `assets:[]` не является готовым загрузчиком арта. Не обходить его записью непроверенных URL в UI.
6. Связать определение предмета, visual bindings и immutable AssetRefs. Цена/редкость/коллекция/доступность живут в своих определениях/предложениях; владение и выбор — в runtime. Проверить exact transitive dependencies.
7. Реализовать отдельный resolver/renderer с закрытым allowlist хранилища и поддерживаемых форматов. **Не расширять текущий AssetSlot произвольным `src`.** Точная граница компонентов принимается в этом последующем этапе.
8. После visual QA и проверки происхождения поместить только реально подключаемые immutable экспорты в `public/assets/game/family_life_v3/<release>/`. Подставить реальные согласованные slug/revision вместо шаблонов. Не перезаписывать bytes прежнего release.
9. Добавить фактическую строку Name/Size/Path/Used-by в `docs/ASSET_MANIFEST.md`. Документировать в контентном manifest bytes/hash/media/profile/source credits; это другой manifest с другой задачей.
10. Проверить все `screens` места, ошибки ресурса, совместимость с полученными вещами и rollback. Выпуск/активация — самостоятельный проверяемый этап. Наличие файла или строки в справочнике не означает публикацию.

Папки и графические файлы из этого списка сейчас не создаются. Старые demo/ULPC/Previews не удаляются и не переименовываются.

## Что не фиксируется до артдирекции

- Exact экспортные размеры, pixel grid и масштаб на реальном WebView: нынешние значения только кандидаты.
- Pixel art/иной окончательный стиль, камера, свет, контур, палитра, пропорции тел и питомцев.
- Обязательная сидячая поза, количество body families/views/цветов и точные hand/seat anchors.
- Отдельный PNG для каждого глаза/брови/материала; разбиение зависит от поддержанного редактирования и перекрытий.
- Универсальный порядок слоёв, spritesheet, FPS, анимационные фазы и atlas format.
- Полный ассортимент «20 причёсок/12 питомцев/100 наград», обязательная графика каждого состояния и сроки производства.
- CDN-путь, компрессия и бюджеты загрузки/памяти без измерений пилота.

Уже фиксируются: стабильные UI-места, отделение текста/controls от рисунка, явное происхождение/версия ресурса, отсутствие персональных данных в общем каталоге, неизменность опубликованных bytes, сохранение выбранного контента при ошибке и совместимость как проверяемый контракт.

## Проверка перед подключением

Для каждого ресурса проверить alpha/canvas/trim offsets, отсутствие clipping и двойных теней/кистей, matching preview/scene, совместимые body/pose/held/hair/headwear комбинации, доступность бесплатной базы, 375/390 px и большие составы семьи, длинные подписи, keyboard/screen reader, missing/unsupported revision и сохранение старых приобретённых ссылок.

Для этапа без графики действует обратная проверка: все места остаются `planned`, в компоненте нет ресурсных элементов/URL, прохождение всего UI не вызывает ни игровых image/media/font запросов, ни API-запросов семьи. Детальный план и ограничения доказательств приведены в [архитектурном аудите](ARCHITECTURE_AUDIT.md).
