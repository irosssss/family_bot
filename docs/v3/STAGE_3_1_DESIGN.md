# Этап 3.1 — решения реализации

Дата: 2026-09-09. Отдельное «Продолжай» запускает ограниченную карточку 3.1 от commit `adfd2421`. Это выбранные технические решения для синтетического фундамента, а не готовая публичная авторизация.

- Код только в `src/v3-server`, миграции только `migrations/v3`. UI не импортирует сервер. Временный PostgreSQL 18.6 создаётся отдельным runner с уникальными именами, labels и собственным паролем; project env и legacy defaults не читаются.
- Схема `rpg_v3`: Account, Family, MemberProfile, Player, CapabilityGrant, AccessBinding, Session. У Player нет роли: взрослый и ребёнок используют один контракт. Composite FK сохраняют семью и member/player binding. Wallet/XP/дел/наград здесь нет.
- IdentityAdapter — dependency-injected доверенный порт. Только тестовый адаптер с `syntheticOnly:true` принимает opaque fixture credential. Он находится в tests/support. Публичного HTTP entry и fallback нет. VerifiedActor выдаётся конкретным экземпляром access service, заморожен и имеет проверяемое внутри процесса происхождение; JSON или копия объекта не проходят guard.
- В начале транзакции берём row lock семьи, затем Account → Member → Player (если есть) → Binding → Session → grants по id. Сначала читаем session/binding только для нахождения семьи; после блокировок всё перечитываем и проверяем. Все guard/revoke и foundation writers используют эту границу. Для отзыва binding/capability/session берётся тот же family lock; CAS revision отвергает устаревшие изменения. Блокировки записей защищают и от параллельного прямого UPDATE соответствующей строки. Прямой SQL не является поддержанным прикладным интерфейсом.
- Guard сверяет текущие IDs, роли/mode, статусы, время session по БД и revisions с выданным actor, затем capability и ресурс этой семьи. Отзыв grants повышает capability revision. Нет решения по одному snapshot интерфейса.
- Account, Family, Member, Binding и Session должны быть active; истёкшая Session запрещена. Для self-effect Player должен быть active. Для own history active/paused допустимы. Player left/archived не получает self-доступ. Административные действия взрослого зависят от active Member и нужного grant; пауза/отсутствие Player их не блокирует. Старый actor после revoke не получает projection под видом retry.
- Ручная проверка собственной доли запрещена. Выбор `adult_self_trusted` — серверная ветка self-submit policy, `child_requires_adult` — другая ветка. Это только eligibility/decision, без attempt и settlement. Review ребёнка возможен у единственного взрослого, с его отдельным grant; статус исторического beneficiary не даёт ему новых прав и сам по себе не запрещает взрослому review.
- Реальные награды имеют отдельную проверку child-only независимо от self-grant. В 3.1 отсутствуют заказ, резерв и выдача. `managed_child`, реальный вход, PIN/recovery и общий девайс остаются отдельным этапом 3.6; fixture adapter проверяет только adult/own_child.
- Семейная покупка расходует личные средства: её eligibility требует adult mode, отдельного family-scope grant и active личного Player. Управление/детская проверка активного взрослого Member допустимы также при left/archived Player; self-history такого Player закрыта.
- Тестовый write marker в отдельной fixture schema доказывает только guard/revoke атомарность. Гонка проверяется двумя соединениями, с наблюдением блокировки PostgreSQL, в обоих порядках. Это не игровой ledger и не idempotency implementation.

Ограничения: production retention, transport, rate limiting, реальная identity verification и миграция настоящих семей не входят в 3.1.
